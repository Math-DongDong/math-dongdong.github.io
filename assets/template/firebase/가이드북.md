# MathDongDong 가이드북 (v4.2)

지금까지의 점검·수정·설계 결정을 한 곳에 모았습니다.
**새 게임을 만들 때, 그리고 문제가 생겼을 때** 이 문서부터 보시면 됩니다.

> **v4.2 핵심**
> · 학생은 **1~3으로 시작하는 학번(숫자 4~5자리) + 4자리 PIN**을 입력합니다. 학교·담당 선생님은 **방을 만든 선생님**을 따릅니다.
> · 인증 방에 들어온 학생은 **학생 관리**에 자동으로 쌓이고, 선생님은 **내 방 학생만** 봅니다 (보안 규칙이 서버에서 막음).
> · 학생 관리에서 접속중 / 다른화면 / 접속 끊김을 봅니다 ([새로고침]을 누를 때만 갱신).
> · 공통 모듈은 `room-auth.js?v=4.2`, `game-kit.js?v=4.2`, `dashboard-header.js?v=4.2`로 맞춥니다.
> · 개인 기록형 대시보드는 같은 닉네임의 기록을 모아 집계하며, 완료 체크포인트는 이후 탈락으로 취소하지 않습니다.
> · 유형 A 템플릿에 **종료 1회 보장**(`gameOver` 플래그)·**학급 요약 카드**·**학생 상세 모달**이 기본으로 들어갑니다 (삼각형 닮음 카드게임에서 정리).

- 배포 절차만 필요하면 → `DEPLOY.md`
- 게임 파일 목록만 필요하면 → `PATCHES.md`

# 0. v4.2 입장 방식 — 먼저 읽으세요

| | A. 빠른 입장 | B. 인증 · 본인 기기 | C. 인증 · 게스트(공용 기기) |
|---|---|---|---|
| 학생이 입력 | 방 코드 | 방 코드 + **학번 · PIN** (처음 1회) | 방 코드 + **학번 · PIN** (매번) |
| 학교 · 선생님 | 없음 | 방을 만든 선생님 것 **자동** | 방을 만든 선생님 것 **자동** |
| 선생님 승인 | 없음 | 없음 | 대시보드 배너에서 승인 |
| 기기에 남는 것 | 닉네임 | 학교 · 학번 · PIN 증명값(평문 아님) · 닉네임 | 없음 (탭을 닫으면 사라짐) |
| 학생 관리에 쌓임 | 아니요 | 예 | 예 |

- **학번**은 `^[1-3]\d{3,4}$` 규칙을 따릅니다. 즉 1~3으로 시작하는 숫자 4~5자리입니다.
  예: `1230`, `11205`. 입력 모달은 `room-auth.js`의 `STUDENT_ID_PATTERN`으로 검사하고,
  길이 제한은 `STUDENT_ID_MAX_LEN`(5)으로 맞춥니다. 정규식만 바꾸지 말고 Firestore 규칙도 함께 확인하세요.
- **PIN**은 처음 등록할 때 학생이 정합니다. 이미 등록된 학번은 PIN이 맞아야 쓰고, 선생님이 초기화한 학번은
  다음 입장 때 입력한 PIN이 새로 등록됩니다. 본인 기기는 증명값만 기억해 다음부터 조용히 확인합니다(원칙 5).
- **학교·선생님**은 `resolveRoomOwner()`가 ① 방 문서의 `creatorSchool`·`creatorName` → ② `teacher_directory/{createdBy}`
  순서로 찾습니다. 둘 다 없거나 학교가 `관리자`이면 인증 입장이 막히므로, **인증 방은 학교명이 있는 선생님만 만듭니다.**
- **기기 주인(학번)이 바뀌면** 이전 학번은 접속 해제되고, 그 기기의 모든 닉네임 기억을 지웁니다(기록 섞임 방지).
- **게임 탭을 떠나면** `presence: 'away'`를 보내 학생 관리에 '다른화면'으로 보입니다.

학번 도용은 네 겹으로 막습니다 — **PIN**(규칙이 해시 대조) · **동시 접속 차단**(45초 신호, 120초 판정) ·
**기기 3대 한도** · **게스트는 교사 승인**.

# 2. 설계 원칙 7가지

새로 만들 때도 이 일곱 가지는 그대로 지켜주세요.
전부 실제로 구멍이 났던 자리에서 나온 것입니다.

## 원칙 1. 학번은 한 곳에만 둔다

| 어디에 | 무엇이 | 누가 읽나 |
|---|---|---|
| `student_auth/{학교_학번}` | 학교·학번·담당 선생님·기기 지문·접속 상태 | 한 개는 누구나(학번 확인용), **목록은 내 학생만** |
| `{게임}_records/{방}/students/{닉}` | 학번 + 게임 요약 | **교사만** |
| `{게임}_records/{방}/records/{자동}` | 순위표용 점수 | **누구나** |
| RTDB `players/{닉}` | 전적·하트비트 | 학생도 읽음 |

**순위표와 RTDB에는 학번을 절대 넣지 않습니다.**
보안 규칙도 `records`에서 `studentId`·`school`·`studentKey` 키를 거부합니다.
대시보드는 닉네임을 열쇠 삼아 **화면에서만** 두 값을 이어 붙입니다.

> v1에서는 `students`가 공개 읽기였습니다. 순위표에 뜬 닉네임 하나로
> `getDoc(students/'용감한 사자')` 를 부르면 그 친구의 학교와 학번이 나왔습니다.

## 원칙 2. 학생에게는 로그인이 없다

그래서 보안 규칙은 "누가 쓰는지"를 알 수 없습니다.
할 수 있는 것은 **무엇을 쓸 수 있는지**를 좁히는 것뿐입니다.

- `nicknames` — 필드를 하나도 넣을 수 없음 (`keys().size() == 0`)
- `guests` — `{status: 'pending'}` 만 쓸 수 있음 (스스로 승인 불가)
- `records` — 학번 계열 키 금지, `score`는 숫자여야 함
- `student_auth` — 정해진 9개 키만, 기기 3대까지, 새 학번 4~5자리, 학교·학번 변경 불가, `presence`는 4가지 값만

값의 범위를 묶어 두면 **사고성 파괴**는 막을 수 있습니다.
악의적 조작까지 막으려면 익명 인증이 필요합니다 (10장 참고).

## 원칙 3. 방 노드를 통째로 읽지 않는다

학생이 실제로 필요한 것은 보통 한두 칸입니다.
통째로 읽으면 전원의 기록·의견·배치가 학생 브라우저로 내려갑니다.

```js
// ❌ get(roomRef(code))
// ✅ get(ref(db, `rooms/${code}/status`))
```

블로토는 이것 때문에 **게임 규칙 자체가 깨져 있었습니다.**
'동시에 몰래 배치'하는 게임인데, 라운드 중 새로고침만 해도 남의 배치가 보였습니다.
그래서 v3에서는 아직 공개하지 않은 제출값을 `submissions` 노드로 분리했습니다.

## 원칙 4. 교사 판정은 서버가 한다

클라이언트의 `window.isApprovedTeacher` 는 **화면만 가립니다.**
브라우저에서 얼마든지 바꿀 수 있습니다.

- **Firestore** — `isTeacher()` 가 `teachers/{uid}.status == 'approved'` 를 서버에서 읽습니다
- **RTDB** — Firestore를 읽을 수 없으므로 `teacher_uids/{uid} === true` 허용 목록을 씁니다
  (승인·취소 시 `account_manager.html` 이 4개 DB에 자동 동기화)
- **'내 학생'·'내 방'도 서버가 판정합니다 (v4.1)** — 같은 학교 + `teachers`에 내 이름이면 내 학생,
  방 문서 `createdBy`가 나면 내 방. 학생 목록·삭제·PIN 초기화, 학번 열람·게스트 승인이 이 판정을 거칩니다.

## 원칙 5. PIN 해시는 클라이언트로 내려보내지 않는다

4자리 PIN은 경우의 수가 1만 개뿐이라, 해시가 새는 순간 끝입니다.
그래서 **"이 값이 맞나요?"만 물어보는 구조**를 씁니다.

```
학생 → student_auth/{키}/gate/{기기지문} 에 { proof } 쓰기 시도
규칙 → 서버에서 private/auth.pinHash 와 대조 → 같으면 허용
학생 ← 성공/실패만 받음.  해시는 브라우저에 오지 않음
```

`private/auth` 는 **교사에게도** 읽기를 막았습니다.
교사가 할 수 있는 일은 초기화와 삭제뿐이고, 그건 읽지 않아도 됩니다.

## 원칙 6. 학생이 입력한 값은 화면에 넣기 전에 반드시 이스케이프

`records`는 로그인 없이 만들 수 있습니다.
닉네임에 코드를 심은 기록을 하나 남겨 두면, **선생님이 대시보드를 여는 순간
교사 세션에서 실행됩니다.**

```js
// ❌ onclick="showStudentModal('${nick}')"
// ✅ data-nick="${escapeHtml(nick)}"  + 이벤트 위임
```

숫자로 쓸 값도 `safeNumber()` 를 거칩니다. `score`에 문자열이 들어올 수 있습니다.

## 원칙 7. 학생의 학교는 방이 정한다 (v4)

학생이 학교를 고르거나 입력하지 않습니다. 방을 만든 선생님의 학교가 곧 학생의 학교입니다.

- 인증 방을 만들 때 방 문서에 `creatorSchool`을 넣습니다. 규칙은 이 값이 **만든 선생님의 학교와 같을 때만** 인증 방을 허락합니다.
- 입장할 때마다 `student_auth.teachers`에 방 선생님 이름을 더합니다 → 학생 관리에 자동으로 쌓입니다.
- 담당 학생이 남은 채 선생님이 학교를 바꾸면 그 학생들이 사라지므로, **정보수정은 담당 학생이 없을 때만 학교를 바꿉니다.**

# 3. 실수 사례집

v2~v4에서 실제로 발견된 것들입니다. **새로 만들 때 같은 자리를 조심하세요.**

## v4 · v4.1에서 고친 것

| 증상 | 원인 | 처리 |
|---|---|---|
| 선생님이 다른 학교 학생 목록을 보고 PIN도 초기화할 수 있음 | v3 규칙이 '승인 교사'면 전부 허락 | 규칙이 '내 학생'(같은 학교 + 담당 이름)만 허락 |
| 기기에서 학번을 바꾸면 이전 학번의 닉네임을 이어받음 | 게임 닉네임만 지우고 방별 닉네임 기억은 남김 | 주인이 바뀌면 모든 게임·방의 닉네임 기억 삭제 |
| PIN을 없앤 v4에서 남의 학번으로 쉽게 입장 | 동시 접속 차단·기기 한도만으로는 부족 | v4.1에서 PIN을 v3 방식 그대로 되살림 |
| PIN 초기화 창에서 다른 학교를 고를 수 있음 | v3 코드를 그대로 되살림 | 선생님은 내 학교로 고정, 관리자만 선택 |
| 한 페이지에서 `room-auth.js`가 두 번 로드될 위험 | 페이지와 game-kit이 서로 다른 `?v=` 주소로 import | 모든 import를 같은 `?v=4.1`로 통일 |
| 학번 입력 규칙이 페이지마다 달라짐 | 4~5자리 길이만 검사하고 시작 숫자 제한을 빠뜨림 | 공통 `STUDENT_ID_PATTERN`의 `^[1-3]\d{3,4}$` 규칙 사용 |
| 좀비헌터에서 완료 학생이 혼합 진행 중으로 되돌아감 | Stage 5 체크포인트의 `isCompleted: true`를 탈락 시 `false`로 덮어씀 | `isClear || Boolean(checkpointRecordRef)`로 완료 상태를 보존 |
| 좀비헌터 점수 기록이 학생별 최신 값만 남음 | 기록을 닉네임 문서 하나에 계속 덮어씀 | 플레이 기록은 누적 저장하고, 대시보드에서 닉네임별 최고점·완료 여부를 집계 |
| 학생 삭제 후 인증 하위 문서가 남음 | Firestore는 부모 삭제만으로 하위 컬렉션을 지우지 않음 | `gate`를 500개 단위로 삭제, `private/auth`는 읽지 않고 직접 삭제한 뒤 부모 삭제 |

## v4.2 (삼각형 닮음 카드게임)에서 정리한 것

| 증상 | 원인 | 처리 |
|---|---|---|
| 한 판이 기록 2건으로 저장됨 | 하트 0 직후의 `setTimeout(endGame)`과 [종료] 버튼이 겹치면 `endGame`이 두 번 실행 | `if (gameOver) return; gameOver = true;`로 종료를 한 번만 처리, `initGame()`에서 해제 |
| 게임오버 화면 위에 문제 모달이 남음 | 모달이 열린 채 하트가 0이 되어 화면만 전환 | `endGame` 첫머리에서 열린 `.modal.show`를 모두 닫음 |
| 다시 도전해 저장에 성공해도 빨간 글씨 | 실패 때 `classList.replace('text-success','text-danger')`만 하고 되돌리지 않음 | `setSaveStatus(text, color)`로 `className`을 통째로 지정 (저장 중 → 성공/실패) |
| 필드 이름을 바꾼 뒤 옛 기록이 0으로 보임 | `level` → `round`로 바꾸고 새 키만 읽음 | 대시보드·엑셀에서 `safeNumber(r.round \|\| r.level)`처럼 옛 키를 대체로 읽음 |

## 치명적이었던 것

| 증상 | 원인 | 교훈 |
|---|---|---|
| 학생 인증 모드 입장이 **항상** 실패 | `freshData` 라는 선언되지 않은 변수. 옵셔널 체이닝(`?.`)은 미선언 변수를 구제하지 못함 | 오타 하나가 기능 전체를 죽입니다. 인증 경로는 반드시 실제 기기로 테스트 |
| 좀비헌터 대시보드에서 교사 세션 탈취 가능 | `onclick="fn('${nick}')"` 에 이스케이프 없이 닉네임 삽입 | 같은 수정을 7개 파일에 복사하면 하나를 놓칩니다 → `game-kit.js` 로 모은 이유 |
| 관리자 계정 탈취 가능 | 교사 등록 시 이름 칸에 스크립트를 넣고, 관리자가 승인 화면을 여는 순간 실행 | 보안 규칙이 자기 승인을 막아도, **관리자 브라우저 안에서 실행되면 우회**됩니다 |
| 게스트가 폰 주인의 닉네임을 이어받음 | 게스트 경로도 "이 기기가 이 방에서 쓰던 이름"을 재사용 | 게스트는 기기의 기억을 **한 줄도** 쓰면 안 됩니다 |
| v1 평문 PIN이 그대로 남아 있음 | v2에서 저장 방식만 바꾸고 기존 데이터를 정리하지 않음 | 저장 구조를 바꾸면 **마이그레이션이 세트**입니다 |

## 조용히 망가져 있던 것

| 증상 | 원인 |
|---|---|
| 교사 PIN 초기화 버튼이 아무 일도 안 함 | 공개 문서의 `pin` 필드를 비웠는데, v2부터 PIN은 그 문서에 없음 |
| 오류가 나도 화면에 아무 반응 없음 | `handleAction` 에 try/catch가 없어 permission-denied가 조용히 사라짐 |
| 게스트 두 번째 입장이 항상 실패 | `guests` 문서에 `create` 만 허용 → 재입장 시 덮어쓰기(update)가 거부 |
| 삭제한 학생이 재등록 불가 | Firestore는 문서를 지워도 하위 컬렉션이 남음. `gate` 또는 `private/auth` 잔존 |
| PIN 상태가 전원 "재설정 대기" | 공개 문서에 `pin` 필드가 없으니 항상 그렇게 표시 |
| 학교에 교사가 없으면 학생이 목록에서 사라짐 | `teachers: []` 인 학생을 걸러낼 '미지정' 필터가 없었음 |
| RTDB 규칙 배포가 거부됨 | `_comment_*` 키를 최상위에 넣음. RTDB는 `rules` 외 키를 허용하지 않음 |

## 순서를 틀려서 났던 것

| 증상 | 원인 |
|---|---|
| 교사 동기화에서 `permission-denied` | `teacher_directory` 는 새 규칙에만 있는데 규칙 배포 **전에** 실행 |
| v1 PIN 정리가 막힘 | 새 규칙이 `pin` 키가 든 문서의 쓰기를 거부. 정리는 규칙 배포 **전에** 해야 함 |

> **교훈**: 규칙과 코드를 함께 바꿀 때는 어느 쪽을 먼저 올리는지가 중요합니다.
> `DEPLOY.md` 의 순서가 그래서 그렇게 되어 있습니다.

## 실시간 게임에서만 났던 것

| 증상 | 원인 |
|---|---|
| 강퇴한 학생이 유령으로 되살아남 | 하트비트를 일반 `update` 로 처리 → `runTransaction` 으로 "없으면 만들지 않음" |
| 새로고침했더니 경기가 몰수패 | `onDisconnect` 예약을 취소하지 않고 `location.reload()` |
| 교실 전체 매칭이 멈춤 | 탭만 켜 둔 유령이 대기열 맨 앞을 막음 → `alive` 신선도 판정 추가 |

| 점수가 두 번 오름 | 양쪽이 각자 결과를 계산 → `counted`/`statsApplied` 플래그 선점 |

## 고르는 법

**질문 1. 학생끼리 실시간으로 서로 영향을 주나요?**
→ 아니오면 **A**

**질문 2. 짝을 지어 겨루나요, 전체가 하나를 만드나요?**
→ 전체가 하나면 **B**

**질문 3. 누가 무엇을 했는지 기록에 남겨야 하나요?**
→ 예면 **C**, 아니오면 **D**

## C와 D의 차이는 딱 하나

겨루는 방식(대기실·매칭·하트비트·onDisconnect)은 **완전히 같습니다.**
D에서는 학생 인증(학번·PIN)과 게스트 승인만 빠집니다.

그런데 **D도 Firestore를 한 가지 용도로는 씁니다 — 닉네임 중복 방지.**

C·D 모두 플레이어 노드의 '키'가 곧 닉네임입니다.
이름이 겹치면 한 학생이 튕기거나 두 사람 전적이 합쳐집니다.
조합이 3,600개(형용사 60 × 동물 60)라 30명 교실에서 **8번에 한 번꼴로** 겹칩니다.

Firestore는 `create` 전용 규칙으로
> "쓰기에 성공한 사람만 그 이름을 갖는다"

를 만들 수 있습니다. 문서가 이미 있으면 `create`가 실패하니, 읽고 나서 쓰는 사이의
경합이 원천적으로 없습니다. RTDB에는 이 방법이 없습니다.

그래서 이름표만 Firestore에 둡니다.

```
{게임}_records/{방}/nicknames/{닉}   ← 필드가 하나도 없는 빈 문서
```

이름표가 없으면 기기 id 기반 충돌 처리로 버티게 되는데,
"내 기록이 맞나요?" 확인창이 학생에게 뜨는 상황이 생깁니다.

## 유형별 데이터 구조

### 유형 A
```
{게임}_records/{방}              방 문서 (roomMode·createdBy·creatorName·creatorSchool)
  ├ students/{닉}                학번 포함, 교사만 읽음
  ├ nicknames/{닉}               빈 문서
  ├ guests/{닉}                  승인 상태만
  └ records/{자동}               순위표용, 공개 읽기, 학번 금지
```

### 유형 B
```
RTDB rooms/{방}
  ├ title            학생이 읽는 한 칸
  ├ phaseOpen        진행 제어, 교사만 씀
  └ items/{자동}     함께 모으는 내용, 읽기·쓰기 공개
RTDB room_index/{방} 방 목록 전용, 교사만
```

### 유형 C
```
RTDB rooms/{방}
  ├ status           학생이 읽는 한 칸
  ├ players/{닉}     전적·하트비트, 전체 읽기는 교사만
  ├ waiting/{닉}     대기열, 전체 공개 (매칭에 필요)
  ├ matches/{id}     경기, 전체 읽기는 교사만
  └ matchLock        매칭 경합 정리
Firestore {게임}_records/{방}   방 문서(roomMode·creatorSchool) + students · nicknames · guests
```

### 유형 D
```
RTDB       유형 C와 동일
Firestore  {게임}_records/{방}/nicknames  ← 이것만
```

블로토는 매칭 대신 '전원이 같은 라운드를 진행'하는 방식이지만,
학생 정보를 쓰지 않고 이름표만 Firestore에 두는 점이 같아 유형 D로 봅니다.
아직 공개되지 않은 제출값을 `submissions` 노드로 분리한 것도 이 유형의 응용입니다
(원칙 3 참고).

# 5. 어느 유형이든 반드시 지킬 것

체크리스트로 쓰세요.

- [ ] **학번은 `students` 에만.** `records`·RTDB 노드는 공개 읽기입니다
- [ ] **`escapeHtml`** — `innerHTML` 에 들어가는 모든 학생 입력값
- [ ] **`onclick="fn('${값}')"` 금지** — `data-*` + 이벤트 위임
- [ ] **`safeNumber`** — 공개 쓰기가 가능한 곳에서 온 숫자
- [ ] **방 노드를 통째로 읽지 않기** — 필요한 한 칸만
- [ ] **교사 아니면 리스너 걸지 않기**
      ```js
      if (!window.isApprovedTeacher && !window.isAdmin) return;
      ```
- [ ] **`teacherAuthChanged` 이벤트 구독** — 교사 로그인은 나중에 도착합니다.
      이 줄이 없으면 대시보드를 열었을 때 방 목록이 비어 보입니다
- [ ] **방 삭제 시 하위 컬렉션 먼저**, `await Promise.all(...)` 로 완료를 기다리기
- [ ] **모달 본문에 학생 입력값을 넣을 때도 이스케이프** — 모달 본문은 `innerHTML` 입니다
- [ ] **인증 방은 `creatorSchool` 저장** — `game-kit`의 `createRoom()`이 해 줍니다. 직접 만들면 학교명 확인도 함께
- [ ] **수정한 모듈의 import 버전 갱신** — 현재 `room-auth.js?v=4.2`, `game-kit.js?v=4.2`, `dashboard-header.js?v=4.2`
- [ ] **종료는 한 번만** — 저장 함수 첫머리에 중복 실행 방지 플래그 (유형 A는 `gameOver`)
- [ ] **기록 필드 이름을 바꾸면 옛 키도 읽기** — `r.새키 || r.옛키`
- [ ] **학생 목록 쿼리에는 학교 + 담당 선생님 조건** — 규칙은 필터가 아닙니다 (8장)

### 대시보드를 키우는 방법 (삼각형 닮음 카드게임 예)

템플릿 대시보드는 세 층으로 되어 있습니다. 게임별 항목은 같은 자리에 덧붙이면 됩니다.

| 층 | 템플릿 기본 | 닮음 카드게임에서 덧붙인 것 |
|---|---|---|
| 학급 요약 카드 (`dash-stat-box`) | 평균 점수 · 평균 정답률 | 닮음 조건(SSS·SAS·AA)별 학급 정답률, 대응점 연결·보너스 정답률 진행 막대 |
| 학생별 표 | 최고 점수 · 정답률 · 플레이 | 종합 성취수준(최고 도달 라운드 기준 상·중·하), 조건별 정답률 열 |
| 학생 상세 모달 (`openDetail`) | 판별 학습 로그 | 조건별 누적 맞/틀 카드, 판마다 조건별 정답률 열 |

- 학급 평균은 **학생별 값의 평균**입니다 (판 수가 많은 학생 쪽으로 쏠리지 않도록). 조건별 정답률처럼 문항 단위 통계는 전체 기록을 합산합니다.
- 유형별 맞/시도는 `sssOk`·`sssTot`처럼 **쌍으로 저장**하면 표·모달·엑셀이 같은 값을 씁니다. `records`는 키 25개 한도이므로 쌍 수를 미리 세어 두세요.
- 성취수준처럼 교사 판단이 들어가는 기준은 `getTier()` 같은 함수 하나로 모아 두고 엑셀 열에도 같은 값을 넣습니다.

## 유형 C·D

1. 템플릿 복사
2. Firestore 컬렉션 이름 정하기 (`_records`)
3. 쓸 Realtime Database 정하기 — **기존 DB 재사용을 권합니다**
4. `★ 여기` 표시를 따라 대전 로직 채우기
5. ①②③④ 표시된 네 곳은 **지우지 마세요**
6. 유형 C는 방을 만들 때 Firestore 방 문서에 `creatorSchool`을 넣습니다 (템플릿에 들어 있음)

## 유형 B, 또는 새 Realtime Database를 쓸 때

Firestore와 달리 **자동으로 되는 게 없습니다.** 네 가지를 해야 합니다.

1. `firebase-config.js` 에 DB 추가하고 export
2. 기존 RTDB 규칙을 백업한 뒤 필요한 경로만 수정해 콘솔에 배포 (규칙 원본은 이 저장소에 없음)
3. 교사 권한 동기화 코드가 해당 DB를 포함하는지 확인
4. 관리자로 **교사 권한 동기화** 다시 실행 (`teacher_uids` 채우기)

기존 DB에 노드만 추가하면 2번만 하면 됩니다.

# 8. 보안 규칙 구조

현재 게시된 규칙은 Firebase Console → Firestore Database → [규칙]에서 확인합니다.
규칙 원본 파일은 이 저장소에 없으므로 게시 규칙을 백업한 뒤 아래 권한 요구사항과 대조하세요.

## 게임 컬렉션은 패턴으로 걸려 있습니다

```
match /{gameCol}/{roomCode} {
  ...
}
function isGameCol(name) { return name.matches('.*_records'); }
```

**새 게임을 추가해도 규칙을 고칠 필요가 없습니다.**
지금 쓰는 게임 컬렉션 7개: `plus_minus_records`, `multiply_divide_records`, `zombiehunter_records`,
`similar_triangle_records`, `gomoku_records`, `rps_records`, `blotto_records`
(소감문 관리의 `studentsreview_records`도 같은 패턴에 걸립니다)

블록 안의 모든 규칙이 `isGameCol(gameCol) &&` 로 묶여 있어,
`teachers` 나 `student_auth` 같은 다른 최상위 컬렉션에는 적용되지 않습니다.

## 하위 컬렉션별 권한 (현재 규칙 기준)

'내 방' = 방 문서의 `createdBy`가 나(또는 빈 값인 옛 방). 관리자는 모든 방이 내 방입니다.

| 경로 | 학생 | 교사 |
|---|---|---|
| `{방}` | get만 (모드·학교 확인) | 만들기(인증 방은 내 학교만) · **내 방만** 고치기·삭제 |
| `students/{닉}` | 쓰기만 (읽기 불가) | **내 방만** 읽기·삭제 |
| `nicknames/{닉}` | 빈 문서 create만 | 목록 · 내 방 삭제 |
| `guests/{닉}` | get + pending으로만 쓰기 | **내 방만** 승인·거절 |
| `records/{자동}` | 읽기 + 검증된 create | 내 방 삭제 |

## student_auth

'내 학생' = 같은 학교 + `teachers`에 내 이름. 관리자는 모든 학생이 내 학생입니다.

| 할 일 | 학생(로그인 없음) | 교사 |
|---|---|---|
| 한 개 읽기 | 가능 (자기 학번 확인) | 가능 |
| 목록 | 불가 | **내 학생만** — 쿼리에 `school ==` + `teachers array-contains` 필수 |
| 만들기·고치기 | 9개 키, 새 학번 `^[1-3]\d{3,4}$`, 학교·학번 변경 불가, `presence` 4가지 | 같음 |
| 학생 문서 삭제 · PIN 초기화 | 불가 | **내 학생만** |
| `gate` 문서 읽기 | 불가 | 불가. 학생 문서의 등록 기기 ID로 경로를 지정해 삭제 |
| `private/auth` 삭제 | 불가 | **내 학생만** delete 가능, read는 불가 |
| PIN 해시(`private/auth`) 읽기 | 불가 | 불가 |

선생님 본인은 `teachers/{uid}`의 이름을 바꿀 수 없고, `teacher_directory`에는 teachers 문서와 같은 학교·이름만 올라갑니다.
이름이 '내 학생'을 가르는 기준이기 때문입니다.

`school ==`와 `teachers array-contains`를 함께 거는 쿼리는 보통 색인 없이 동작합니다.
"색인이 필요합니다" 오류가 나면 브라우저 콘솔의 링크를 눌러 만들면 됩니다.

## RTDB는 별개입니다

RTDB 규칙은 Firestore를 읽을 수 없습니다.
그래서 각 DB마다 `teacher_uids` 허용 목록을 두고, 승인 시 자동으로 채웁니다.

**RTDB의 `.write` 는 아래로 전파되어 자식 규칙으로 되돌릴 수 없습니다.**
`$nick` 에 `.write: true` 를 주면 그 아래 `score` 를 교사 전용으로 막을 수 없습니다.
`.validate` 로 값의 범위를 묶는 것까지가 한계입니다.

RTDB 규칙 4개는 Firestore 규칙과 별개입니다. v4.2 템플릿을 배포하기 전에 현재 콘솔 규칙이 새 기능에서 쓰는 경로·필드를 허용하는지 확인하세요.
규칙 원본 파일은 이 저장소에 포함되어 있지 않으므로, Firebase Console의 게시된 규칙을 백업한 뒤 수정해야 합니다.

# 9. 문제 해결

## `permission-denied` 가 났을 때

Firebase Console의 Firestore/RTDB 규칙 탭과 브라우저 F12 콘솔을 확인하세요.
`migrate_v3.html` 진단 도구는 현재 저장소에 포함되어 있지 않습니다.

원인은 대개 셋 중 하나입니다.

| 증상 | 원인 |
|---|---|
| `teacher_directory` 쓰기 거부 | 아직 새 규칙을 배포하지 않음 |
| `teachers` 목록 읽기 거부 | 규칙의 `isAdmin()` uid가 실제와 다름 |
| `student_auth` 쓰기 거부 | 그 문서에 v1 `pin` 필드가 남아 있음 |
| `student_auth` 목록 거부 | 쿼리에 `school`·담당 교사 조건이 있는지 확인하고, 화면 캐시는 강력 새로고침 |

## 학생이 "학교 정보를 찾지 못했습니다"라고 할 때

방을 만든 선생님의 학교명이 없거나 `관리자`입니다. 상단 메뉴 → **정보수정**에서 실제 학교명으로 바꾼 뒤
**방을 새로 만드세요.** (v4.2에서도 학생이 학교를 고르는 드롭다운은 없습니다)

## 선생님이 실시간 게임 방을 못 만들 때

해당 DB의 `teacher_uids` 에 uid가 없습니다.
규칙을 배포한 뒤 **2번**을 실행하세요.

## 학생이 "존재하지 않는 방"이라고 할 때

오목 — 기존 방에 `status` 값이 없을 수 있습니다. 기존 방 데이터에 상태 필드를 보충하거나 새 방을 만드세요.

## 대시보드 방 목록이 비었을 때

`teacherAuthChanged` 구독이 빠졌는지 확인하세요.
교사 로그인 결과는 페이지가 뜬 뒤에 도착합니다.

## 학생이 PIN을 잊었을 때

**학생 관리** → 해당 학생 → PIN 초기화, 또는 게임 대시보드 상단 **[PIN 초기화]**(내 학교·내 방 학생만).
학생은 다음 접속 때 새 PIN을 설정합니다.

## 기기를 바꿔 한도(3대)를 넘겼을 때

**학생 관리** 페이지 → 기기 초기화.

## 그 밖의 v4.1 증상

| 증상 | 원인과 조치 |
|---|---|
| 학생 관리에 학생이 안 보임 | 빠른 입장 방이었거나(학번을 받지 않음) 다른 선생님 방 학생입니다. 관리자는 **전체 선생님**으로 확인 |
| 학생 관리 상태가 안 바뀜 | 실시간이 아닙니다. [새로고침]을 누르세요 (기준 시각은 버튼 아래) |
| 학생 관리: "학생 정보를 불러오지 못했습니다" | 보안 규칙과 화면 쿼리를 확인하고 강력 새로고침. 콘솔에 색인 링크가 보이면 눌러 색인 생성 |
| 정보수정: "담당 학생 N명이 있어 학교를 바꿀 수 없습니다" | 의도된 제한. 학생을 삭제하거나 담당 선생님에서 빼면 바꿀 수 있습니다 |
| 인증 방 만들기 실패 | 규칙이 `creatorSchool` ≠ 내 학교면 거부합니다. 정보수정의 학교명 확인 후 새로고침 |
| 학생: "보안 연결 필요" | https가 아닌 주소(file:// 등)로 열었습니다. 배포 주소로 여세요 |
| 다른 학생이 내 학번으로 들어옴 | PIN이 샌 것입니다. **PIN 초기화 + 기기 초기화** 후 본인이 새 PIN으로 입장 |

# 10. 알고 쓰셔야 하는 한계

학생에게 로그인이 없으므로, 아래는 규칙만으로 막을 수 없습니다.
**수업 진행에는 지장이 없는 수준**이라 그대로 두었습니다.

1. 콘솔에서 다른 닉네임의 기록을 덮어쓰는 것
2. 자기 점수나 승수를 직접 올리는 것 (값의 범위는 제한했습니다)
3. 아직 등록하지 않은 학번의 PIN을 남이 먼저 만들어 두는 것
   → 선생님이 **학생 관리 → PIN 초기화**로 풀어주시면 됩니다
4. 남이 쓸 닉네임을 미리 차지하는 것
5. 4자리 PIN 전수 대입 — PBKDF2 10만 회로 비싸게 만들 뿐 막지는 못합니다
6. 같은 학교에 같은 이름의 선생님이 둘이면 서로의 학생이 보입니다 ('내 학생'을 이름으로 가르기 때문)
7. '담당 학생이 있으면 학교 변경 금지'는 규칙으로 셀 수 없어 정보수정 화면에서만 막습니다

## App Check가 막는 것과 못 막는 것

- ✅ 페이지 밖에서 오는 요청 (curl, 외부 스크립트)
- ❌ **학생이 F12로 페이지 안에서 호출하는 것**

App Check는 보안 규칙을 대체하지 않습니다.
콘솔에서 "적용(Enforce)"까지 눌러야 효과가 있고, RTDB는 4개 인스턴스 각각 확인해야 합니다.

## 근본 해결책

**Firebase 익명 인증**입니다.
학생도 uid를 갖게 되면 `players/{닉}.uid == auth.uid` 같은 소유권 규칙을 쓸 수 있어
위 네 가지가 모두 막힙니다.

- 학생 화면에는 아무 변화가 없습니다 (로그인 창이 뜨지 않습니다)
- `signInAnonymously(auth)` 한 줄 + 규칙 수정
- 지금 구조 위에 나중에 얹을 수 있습니다

여유가 생기면 다음 단계로 고려해보세요.

# 11. 학생 관리 페이지

## 누가 무엇을 보나

| | 학교 | 담당 선생님 |
|---|---|---|
| 선생님 | 내 학교로 고정 | 내 이름으로 고정 — **내 방에 들어온 학생만** (게스트 포함) |
| 관리자 | 골라서 봄 | 한 명씩 고르거나 **전체 선생님** |

'담당 미지정' 필터는 없습니다. 기기를 등록하는 순간 방 선생님이 담당 선생님이 되기 때문입니다.
담당 선생님이 비어 있는 예전 학생은 관리자가 **전체 선생님**으로 봅니다.

## 할 수 있는 일

PIN 초기화 · 기기 초기화 · 접속 해제 · 담당 선생님 수정 · 삭제 (개별·일괄). PIN 열에는 설정됨 / 재설정 대기가 보입니다.
삭제는 학생 문서에 남아 있는 등록 기기 ID로 `gate/{기기ID}` 문서를 지정해 배치 삭제하고, 읽기 권한이 없는 `private/auth`는 경로를 지정해 직접 삭제한 뒤 학생 문서를 지웁니다. PIN 증명값을 포함한 `gate` 문서의 list/read 권한은 열지 않습니다.
이전 버전에서 기기 초기화로 등록 ID가 이미 지워진 고아 `gate` 문서까지 전부 찾아내려면 관리자 콘솔 또는 서버 측 정리 작업이 필요합니다. 클라이언트가 목록을 읽게 해 PIN 증명값을 노출하지 마세요.

## 접속 상태

좌표평면 오목과 같은 색입니다. 표는 상태 순(접속중이 위), 같은 상태 안에서는 학번 순입니다.

| 표시 | 뜻 |
|---|---|
| 🟢 접속중 | 게임 화면을 보고 있음 (120초 안에 신호) |
| 🟡 다른화면 | 게임 탭을 떠나 다른 탭·앱을 보는 중 |
| 🔵 승인 대기 | 게스트가 선생님 승인을 기다리는 중 |
| 🔴 접속 끊김 | 30분 안에 신호가 끊김 (창을 정상적으로 닫지 않음·네트워크) |
| ⚪ 미접속 | 정상적으로 나갔거나 마지막 신호가 30분보다 오래됨 |

**실시간이 아닙니다.** 서버에서 읽는 것은 페이지를 열 때, 학교를 바꿀 때, **[새로고침]**을 누를 때뿐이고,
상태는 그 시각 기준입니다. 버튼으로 한 작업은 서버에 쓰고 화면에만 바로 반영합니다.

## 선생님 학교 변경

학생 관리에서 학생을 삭제하거나 담당 선생님에서 뺀 뒤 바꾸세요.

# 12. 설문·소감문 통합 템플릿

기존 두 관리 페이지의 핵심을 새 템플릿 하나로 조합했습니다.

| 파일 | 역할 |
|---|---|
| `pages/admin/formbuilder.html` | 실제 범용 문항형 설문 빌더 |
| `pages/admin/studentsreviewsystem.html` | 실제 활동별 소감문·Gemini AI 관리 |
| `assets/template/firebase/설문-소감문-통합형.html` | 새 활동을 시작할 때 복사하는 통합 템플릿 |

통합 템플릿에는 문항 추가·분기·필수값 및 전화번호/이메일 검사, 학생 응답 저장·수정, 마감 예약,
교사 피드백·교사 시점 기록 편집, Gemini 초안 생성, 응답 엑셀 다운로드가 포함됩니다. AI 초안 생성에는
설문 답변만 Gemini API로 전송하며 학번은 전송하지 않습니다. 생성 결과는 교사가 확인·수정한 뒤 저장합니다.
교사 검토는 `responses/{학번}` 문서의 `feedback`과 `teacherView` 필드에 저장됩니다. 기존
`studentsreviewsystem.html`의 프롬프트 보관함과 일괄 생성 기능은 해당 페이지에 유지됩니다.

## 학생 인증과 중복 응답

- 학생은 `renderRoomEntrance()` 공통 흐름을 사용합니다. 인증 모드 학번은 `^[1-3]\d{3,4}$`를 만족해야 하며,
  학교는 방을 만든 선생님을 따릅니다. PIN은 4자리 숫자입니다.
- 인증 학생 응답은 `custom_forms/{방}/responses/{학번}`을 문서 ID로 사용합니다. 트랜잭션이 기존 문서를 확인하므로
  같은 학생이 다시 제출하면 새 응답을 중복 생성하지 않고 기존 답을 수정합니다. 응답 수는 첫 생성 때만 증가합니다.
- 양식에 응답이 하나라도 생기면 질문 구조를 잠급니다. 질문 변경이 필요하면 양식을 복제해 새 방을 만듭니다.

## 데이터 구조

```
custom_forms/{방}                     ← 설문 제목·설명·formSchema·상태·응답 수
  ├─ responses/{학번}                ← 답변·수정 시각·교사 검토
  │    ├─ answers: {문항ID: 답}
  │    ├─ feedback: 교사 피드백
  │    ├─ feedbackUpdatedAt: 피드백 수정 시각
  │    ├─ teacherView: 교사 시점 관찰 기록
  │    └─ teacherViewUpdatedAt: 교사 시점 수정 시각
  ├─ students/{닉네임}                ← 인증 학생·게스트 입장표
  └─ guests/{닉네임}                  ← 승인 상태
```

Firestore 규칙은 교사에게 응답 문서의 `feedback`, `feedbackUpdatedAt`, `teacherView`,
`teacherViewUpdatedAt` 갱신을 허용해야 합니다. PIN·학번 소유권 등 나머지 응답 검증은 기존 규칙대로 유지하세요.

## 템플릿을 둘 위치에 복사할 때

통합 템플릿은 `assets/template/firebase/` 안에 있습니다. 다른 페이지 디렉터리로 복사하면 `../../../js/`와
`../../../assets/` 같은 상대경로를 새 위치에 맞춰 조정하고, `room-auth.js?v=4.2`를 실제 페이지와 동일 버전으로 유지하세요.

# 13. 우리반 관계지도

구글 앱스스크립트(시트 4개)로 만들었던 학급 관계 설문을 Firestore로 옮긴 페이지입니다. `pages/admin/relationmap.html` 한 파일에 학생 설문과 교사 화면이 함께 있습니다.
화면은 앱스스크립트 `index.html`(칠판 디자인 · vis-network 관계지도 · 학생 상세 Drawer · 제출 도장)을 그대로 따르고, 로그인과 저장만 바꿨습니다.
**아래 규칙 블록을 Firebase 콘솔에 추가해야 동작합니다.**

| | 앱스스크립트 버전 | Firestore 버전 |
|---|---|---|
| 학생 로그인 | 학번 + 비밀번호 (초기 비밀번호 → 변경) | 첫 화면 [학생] 탭: 반 코드 → 학번 + 4자리 PIN (`room-auth.js` 공통 흐름, 게스트 승인 포함) |
| 교사 로그인 | 교사 비밀번호 | 첫 화면 [교사] 탭: 구글 로그인 · 승인된 교사 |
| 반 | 시트 하나 = 반 하나 | 반 코드로 여러 반 (반 줄의 [＋ 새 반]) |
| 비밀번호 초기화 | 웹 앱 명단 | [⚙️ 관리] 탭 명단의 [PIN 초기화] (`resetStudentPin`, 이 반에 들어온 학생만) |
| 설문월 · 마감예약 | `설문월` 시트 | 반 문서의 `months`. 마감·다시 열기·예약·삭제는 [설문 달] 줄, 새 달 시작은 [⚙️ 관리] 탭. 마감 예약 시각은 보안 규칙이 강제 |
| 관계 분석 · 온톨로지 추론 | 서버(`code.gs`) | 교사 브라우저에서 같은 규칙(①~⑥)으로 계산 |
| 수정 권한 | 지난 답을 불러와 고침 | **처음부터 다시 제출** (아래 '알고 쓰셔야 하는 차이' 1번) |
| 예시 데이터 | 시트에 채움 | [예시로 미리보기] — 화면에서만 보이고 저장하지 않음 |

## 쓰는 순서

1. 첫 화면 [교사] 탭에서 구글 로그인 → [＋ 새 반] (반 이름, 이번 달 설문 바로 시작)
2. [⚙️ 관리] 탭 → 학생 명단 등록. 엑셀에서 「번호 학번 이름」 열을 복사해 붙여넣으면 한 번에 들어갑니다.
3. 학생은 QR 또는 반 코드로 들어와 학번·PIN 인증 → 한 장짜리 설문 제출 (명단에 있는 학번만)
4. [🗺️ 관계지도] 탭에서 [↻ 새로고침]으로 최신 응답 확인, [📋 학생 응답] 탭에서 표 · 응답 엑셀 · 수정 권한

관계지도에서 끌어 옮긴 학생 자리는 그 브라우저에 반마다 기억됩니다. [배치 다시 하기]를 누르면 새로 배치합니다.

## 데이터 구조

```
relation_maps/{반 코드}               반 문서 — 학생도 get (친구를 고르려면 명단 이름이 필요)
  │  createdBy · creatorName · creatorSchool · roomMode('auth') · memo
  │  roster: { 학번: { no, name, active } }
  │  months: { 'yyyy-MM': { status('open'|'closed'), openedAt, closeAt } }
  ├ responses/{yyyy-MM}_{학번}         응답 — 선생님만 읽음 (학생 본인도 못 읽음)
  │    month · studentId · deviceFp · climate(1~5) · climateReason · submittedAt
  │    positive: [{ id: 학번, tags, text }] 최대 3 (배열 순서 = 순위) · negative 최대 2
  ├ receipts/{yyyy-MM}_{학번}          제출 여부만 — 누구나 get (학생 화면의 '이미 제출' 판정)
  │    month · studentId · submittedAt · editAllowed
  ├ students/{학번}                    room-auth 입장표 (게스트 승인 배너)
  └ guests/{학번}                      게스트 승인 상태
```

## 보안 설계

- **`_records` 이름을 쓰지 않았습니다.** `.*_records` 패턴의 `records`는 공개 읽기라 "불편한 친구" 같은 응답을 담을 수 없습니다. 전용 컬렉션에 전용 규칙을 둡니다.
- **응답은 PIN 게이트와 한 batch로만 씁니다.** 학생 화면은 `student_auth/{학교_학번}/gate/{기기}`에 증명값을 다시 쓰면서 같은 batch에 응답과 제출 표시를 씁니다.
  게이트 쓰기는 기존 규칙이 PIN 해시와 대조하고(원칙 5), 응답 규칙은 `getAfter()`로 그 게이트가 이번 요청에서 갱신됐는지(`at == request.time`) 확인합니다.
  학번만 알아서는 남의 이름으로 제출할 수 없습니다.
- **제출한 답은 학생 본인도 다시 읽지 못합니다.** 로그인이 없는 학생에게 '본인만 읽기'를 규칙으로 줄 방법이 없어서, 학생 화면은 내용이 없는 `receipts`만 읽습니다.
- **증명값**: 본인 기기는 room-auth가 저장한 증명값을, 게스트는 입장 때 입력한 PIN으로 만든 증명값(메모리에만)을 씁니다. 거부되면 PIN을 한 번 더 받아 다시 시도합니다.

## Firestore 규칙 (콘솔에 추가)

Firebase Console → Firestore Database → [규칙]에서 현재 규칙을 백업한 뒤, `match /databases/{database}/documents { ... }` 안쪽 맨 아래에 붙여 넣습니다.
기존 규칙은 고치지 않습니다.

```
    // ═══ 우리반 관계지도 (pages/admin/relationmap.html) — 가이드북 13장 ═══
    match /relation_maps/{roomCode} {
      // ★ 기존 isAdmin()과 같은 관리자 uid
      function rmAdmin() {
        return request.auth != null && request.auth.uid == '81v0uN5YhFOFXtxn9xisGh5CTka2';
      }
      function rmTeacher() {
        return request.auth != null
          && get(/databases/$(database)/documents/teachers/$(request.auth.uid)).data.status == 'approved';
      }
      function rmOwner() {
        return rmAdmin() || (rmTeacher()
          && get(/databases/$(database)/documents/relation_maps/$(roomCode)).data.createdBy == request.auth.uid);
      }
      function rmRoomExists() {
        return exists(/databases/$(database)/documents/relation_maps/$(roomCode));
      }
      // 학생 제출: 응답 · 제출 표시 · PIN 게이트를 한 batch로 쓸 때만 허용
      function rmStudentSubmit(responseId) {
        let d = request.resource.data;
        let room = get(/databases/$(database)/documents/relation_maps/$(roomCode)).data;
        let period = room.months[d.month];
        let authKey = room.creatorSchool.replace('[.]', '_') + '_' + d.studentId;
        return d.keys().hasOnly(['month', 'studentId', 'deviceFp', 'climate', 'climateReason', 'positive', 'negative', 'submittedAt'])
          && d.keys().hasAll(['month', 'studentId', 'deviceFp', 'climate', 'climateReason', 'positive', 'negative', 'submittedAt'])
          && d.month is string && d.studentId is string && d.deviceFp is string
          && responseId == d.month + '_' + d.studentId
          && d.studentId in room.roster
          && room.roster[d.studentId].active == true
          && period.status == 'open'
          && (period.get('closeAt', null) == null || request.time < period.closeAt)
          && d.submittedAt == request.time
          && d.climate is int && d.climate >= 1 && d.climate <= 5
          && d.climateReason is string && d.climateReason.size() <= 300
          && d.positive is list && d.positive.size() <= 3
          && d.negative is list && d.negative.size() <= 2
          && getAfter(/databases/$(database)/documents/student_auth/$(authKey)/gate/$(d.deviceFp)).data.at == request.time
          && getAfter(/databases/$(database)/documents/relation_maps/$(roomCode)/receipts/$(responseId)).data.submittedAt == request.time
          && (!exists(/databases/$(database)/documents/relation_maps/$(roomCode)/receipts/$(responseId))
              || get(/databases/$(database)/documents/relation_maps/$(roomCode)/receipts/$(responseId)).data.editAllowed == true);
      }

      // 반 문서: 학생은 get만, 목록·쓰기는 만든 선생님과 관리자
      allow get: if true;
      allow list: if rmAdmin() || (rmTeacher() && resource.data.createdBy == request.auth.uid);
      allow create: if request.auth != null
        && request.resource.data.createdBy == request.auth.uid
        && request.resource.data.roomMode == 'auth'
        && request.resource.data.roster is map
        && request.resource.data.months is map
        && (rmAdmin() || (rmTeacher()
          && request.resource.data.creatorSchool == get(/databases/$(database)/documents/teachers/$(request.auth.uid)).data.school));
      allow update: if (rmAdmin() || (rmTeacher() && resource.data.createdBy == request.auth.uid))
        && request.resource.data.createdBy == resource.data.createdBy
        && request.resource.data.creatorSchool == resource.data.creatorSchool
        && request.resource.data.roomMode == 'auth'
        && request.resource.data.roster is map
        && request.resource.data.months is map;
      allow delete: if rmAdmin() || (rmTeacher() && resource.data.createdBy == request.auth.uid);

      // 응답: 선생님만 읽음
      match /responses/{responseId} {
        allow read, delete: if rmOwner();
        allow create, update: if rmStudentSubmit(responseId);
      }

      // 제출 표시: 내용 없이 제출 여부 · 수정 권한만
      match /receipts/{receiptId} {
        allow get: if true;
        allow list, delete: if rmOwner();
        allow update: if rmOwner()
          && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['editAllowed'])
          && request.resource.data.editAllowed is bool;
        allow create, update: if request.resource.data.keys().hasOnly(['month', 'studentId', 'submittedAt', 'editAllowed'])
          && receiptId == request.resource.data.month + '_' + request.resource.data.studentId
          && request.resource.data.editAllowed == false
          && request.resource.data.submittedAt == request.time
          && getAfter(/databases/$(database)/documents/relation_maps/$(roomCode)/responses/$(receiptId)).data.submittedAt == request.time;
      }

      // room-auth 입장표 · 게스트 승인 (8장 게임 방과 같은 권한)
      match /students/{studentKey} {
        allow read, delete: if rmOwner();
        allow update: if rmOwner();
        allow create, update: if rmRoomExists()
          && request.resource.data.keys().hasOnly(['nickname', 'school', 'studentId', 'studentKey', 'teachers', 'status', 'isGuest', 'enteredAt', 'requestedAt'])
          && request.resource.data.status in ['online', 'pending', 'offline', 'rejected'];
      }
      match /guests/{guestKey} {
        allow get, delete: if true;
        allow list: if rmOwner();
        allow create, update: if rmOwner()
          || (rmRoomExists() && request.resource.data.keys().hasOnly(['status']) && request.resource.data.status == 'pending');
      }
    }
```

- `rmAdmin()`의 uid는 기존 `isAdmin()`과 같아야 합니다.
- 3명 · 2명 · 300자는 `relationmap.html`의 `SURVEY_CONFIG`(max · `climateReasonMax`)와 같아야 합니다. 한쪽만 바꾸면 제출이 거부됩니다.
- 규칙에서 학생 인증 키(`학교_학번`)를 다시 만들 때 학교명의 `.`만 `_`로 바꿉니다. 학교명 검사(`SCHOOL_RE`)상 다른 특수문자는 들어오지 않습니다.
- 학생 제출은 기존 `student_auth/{키}/gate/{기기}` 규칙(증명값 = PIN 해시)에 기댑니다. 그 규칙은 바꾸지 마세요.

게시 전에 [규칙] 탭의 플레이그라운드로 확인하세요.

| 시험 | 기대 |
|---|---|
| 로그인 없이 `relation_maps/{코드}` get | 허용 |
| 로그인 없이 `relation_maps/{코드}/responses/{달_학번}` get | 거부 |
| 로그인 없이 `relation_maps/{코드}/receipts/{달_학번}` get | 허용 |
| 반을 만든 선생님 uid로 `responses` 목록 | 허용 |
| 다른 선생님 uid로 `responses` 목록 | 거부 |
| 로그인 없이 `responses` 문서 create (게이트 갱신 없이) | 거부 |

## 알고 쓰셔야 하는 차이와 한계

1. **수정 권한을 주면 학생은 처음부터 다시 제출합니다.** 앱스스크립트처럼 지난 답을 불러오려면 학생에게 응답 읽기를 열어야 하는데,
   그러면 반 코드와 학번만 아는 친구도 그 답을 읽을 수 있습니다. 다시 제출하면 이전 응답을 대신하고 권한은 저절로 사라집니다.
2. **명단 이름은 반 코드를 아는 사람이 읽을 수 있습니다.** 학생이 친구를 이름으로 고르려면 필요합니다. 응답 내용은 해당하지 않습니다.
3. **실시간이 아닙니다.** 교사 화면은 반을 고를 때와 [새로고침]을 누를 때 읽습니다. 게스트 승인 배너만 실시간입니다.
4. **명단에서 지운 학생의 응답은 남습니다.** 관계지도에서만 빠지고, 같은 학번으로 다시 추가하면 돌아옵니다. 잠시 빼려면 [참여 멈추기]를 쓰세요.
5. 10장의 한계(4자리 PIN 전수 대입 등)는 그대로입니다.
