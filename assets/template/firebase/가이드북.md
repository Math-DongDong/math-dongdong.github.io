# MathDongDong 가이드북 (v4.1)

지금까지의 점검·수정·설계 결정을 한 곳에 모았습니다.
**새 게임을 만들 때, 그리고 문제가 생겼을 때** 이 문서부터 보시면 됩니다.

> **v4.1 핵심**
> · 학생은 **학번(숫자 4~5자리) + 4자리 PIN**만 입력합니다. 학교·담당 선생님은 **방을 만든 선생님**을 따릅니다.
> · 인증 방에 들어온 학생은 **학생 관리**에 자동으로 쌓이고, 선생님은 **내 방 학생만** 봅니다 (보안 규칙이 서버에서 막음).
> · 학생 관리에서 접속중 / 다른화면 / 접속 끊김을 봅니다 ([새로고침]을 누를 때만 갱신).
> · 게임 7개가 모두 `game-kit.js`를 쓰고, 모듈 주소는 전부 `?v=4.1`입니다.

- 배포 절차만 필요하면 → `DEPLOY.md`
- 게임 파일 목록만 필요하면 → `PATCHES.md`

# 0. v4.1 입장 방식 — 먼저 읽으세요

| | A. 빠른 입장 | B. 인증 · 본인 기기 | C. 인증 · 게스트(공용 기기) |
|---|---|---|---|
| 학생이 입력 | 방 코드 | 방 코드 + **학번 · PIN** (처음 1회) | 방 코드 + **학번 · PIN** (매번) |
| 학교 · 선생님 | 없음 | 방을 만든 선생님 것 **자동** | 방을 만든 선생님 것 **자동** |
| 선생님 승인 | 없음 | 없음 | 대시보드 배너에서 승인 |
| 기기에 남는 것 | 닉네임 | 학교 · 학번 · PIN 증명값(평문 아님) · 닉네임 | 없음 (탭을 닫으면 사라짐) |
| 학생 관리에 쌓임 | 아니요 | 예 | 예 |

- **학번**은 학년·반·번호를 붙여 씁니다. `1학년 2반 30번 → 1230`, `1학년 12반 5번 → 11205` (입력칸 예시 `예: 1230`).
  자릿수를 바꾸려면 `room-auth.js`의 `STUDENT_ID_PATTERN`·`STUDENT_ID_MAX_LEN` 두 줄만 고칩니다.
- **PIN**은 처음 등록할 때 학생이 정합니다. 이미 등록된 학번은 PIN이 맞아야 쓰고, 선생님이 초기화한 학번은
  다음 입장 때 입력한 PIN이 새로 등록됩니다. 본인 기기는 증명값만 기억해 다음부터 조용히 확인합니다(원칙 5).
- **학교·선생님**은 `resolveRoomOwner()`가 ① 방 문서의 `creatorSchool`·`creatorName` → ② `teacher_directory/{createdBy}`
  순서로 찾습니다. 둘 다 없거나 학교가 `관리자`이면 인증 입장이 막히므로, **인증 방은 학교명이 있는 선생님만 만듭니다.**
- **기기 주인(학번)이 바뀌면** 이전 학번은 접속 해제되고, 그 기기의 모든 닉네임 기억을 지웁니다(기록 섞임 방지).
- **게임 탭을 떠나면** `presence: 'away'`를 보내 학생 관리에 '다른화면'으로 보입니다.

학번 도용은 네 겹으로 막습니다 — **PIN**(규칙이 해시 대조) · **동시 접속 차단**(45초 신호, 120초 판정) ·
**기기 3대 한도** · **게스트는 교사 승인**.

# 2. 설계 원칙 7가지

새로 만들 때도 이 일곱 가지는 그대로 지켜주세요.
전부 실제로 구멍이 났던 자리에서 나온 것입니다.

## 원칙 1. 학번은 한 곳에만 둔다

| 어디에 | 무엇이 | 누가 읽나 |
|---|---|---|
| `student_auth/{학교_학번}` | 학교·학번·담당 선생님·기기 지문·접속 상태 | 한 개는 누구나(학번 확인용), **목록은 내 학생만** |
| `{게임}_records/{방}/students/{닉}` | 학번 + 게임 요약 | **교사만** |
| `{게임}_records/{방}/records/{자동}` | 순위표용 점수 | **누구나** |
| RTDB `players/{닉}` | 전적·하트비트 | 학생도 읽음 |

**순위표와 RTDB에는 학번을 절대 넣지 않습니다.**
보안 규칙도 `records`에서 `studentId`·`school`·`studentKey` 키를 거부합니다.
대시보드는 닉네임을 열쇠 삼아 **화면에서만** 두 값을 이어 붙입니다.

> v1에서는 `students`가 공개 읽기였습니다. 순위표에 뜬 닉네임 하나로
> `getDoc(students/'용감한 사자')` 를 부르면 그 친구의 학교와 학번이 나왔습니다.

## 원칙 2. 학생에게는 로그인이 없다

그래서 보안 규칙은 "누가 쓰는지"를 알 수 없습니다.
할 수 있는 것은 **무엇을 쓸 수 있는지**를 좁히는 것뿐입니다.

- `nicknames` — 필드를 하나도 넣을 수 없음 (`keys().size() == 0`)
- `guests` — `{status: 'pending'}` 만 쓸 수 있음 (스스로 승인 불가)
- `records` — 학번 계열 키 금지, `score`는 숫자여야 함
- `student_auth` — 정해진 9개 키만, 기기 3대까지, 새 학번 4~5자리, 학교·학번 변경 불가, `presence`는 4가지 값만

값의 범위를 묶어 두면 **사고성 파괴**는 막을 수 있습니다.
악의적 조작까지 막으려면 익명 인증이 필요합니다 (10장 참고).

## 원칙 3. 방 노드를 통째로 읽지 않는다

학생이 실제로 필요한 것은 보통 한두 칸입니다.
통째로 읽으면 전원의 기록·의견·배치가 학생 브라우저로 내려갑니다.

```js
// ❌ get(roomRef(code))
// ✅ get(ref(db, `rooms/${code}/status`))
```

블로토는 이것 때문에 **게임 규칙 자체가 깨져 있었습니다.**
'동시에 몰래 배치'하는 게임인데, 라운드 중 새로고침만 해도 남의 배치가 보였습니다.
그래서 v3에서는 아직 공개하지 않은 제출값을 `submissions` 노드로 분리했습니다.

## 원칙 4. 교사 판정은 서버가 한다

클라이언트의 `window.isApprovedTeacher` 는 **화면만 가립니다.**
브라우저에서 얼마든지 바꿀 수 있습니다.

- **Firestore** — `isTeacher()` 가 `teachers/{uid}.status == 'approved'` 를 서버에서 읽습니다
- **RTDB** — Firestore를 읽을 수 없으므로 `teacher_uids/{uid} === true` 허용 목록을 씁니다
  (승인·취소 시 `account_manager.html` 이 4개 DB에 자동 동기화)
- **'내 학생'·'내 방'도 서버가 판정합니다 (v4.1)** — 같은 학교 + `teachers`에 내 이름이면 내 학생,
  방 문서 `createdBy`가 나면 내 방. 학생 목록·삭제·PIN 초기화, 학번 열람·게스트 승인이 이 판정을 거칩니다.

## 원칙 5. PIN 해시는 클라이언트로 내려보내지 않는다

4자리 PIN은 경우의 수가 1만 개뿐이라, 해시가 새는 순간 끝입니다.
그래서 **"이 값이 맞나요?"만 물어보는 구조**를 씁니다.

```
학생 → student_auth/{키}/gate/{기기지문} 에 { proof } 쓰기 시도
규칙 → 서버에서 private/auth.pinHash 와 대조 → 같으면 허용
학생 ← 성공/실패만 받음.  해시는 브라우저에 오지 않음
```

`private/auth` 는 **교사에게도** 읽기를 막았습니다.
교사가 할 수 있는 일은 초기화와 삭제뿐이고, 그건 읽지 않아도 됩니다.

## 원칙 6. 학생이 입력한 값은 화면에 넣기 전에 반드시 이스케이프

`records`는 로그인 없이 만들 수 있습니다.
닉네임에 코드를 심은 기록을 하나 남겨 두면, **선생님이 대시보드를 여는 순간
교사 세션에서 실행됩니다.**

```js
// ❌ onclick="showStudentModal('${nick}')"
// ✅ data-nick="${escapeHtml(nick)}"  + 이벤트 위임
```

숫자로 쓸 값도 `safeNumber()` 를 거칩니다. `score`에 문자열이 들어올 수 있습니다.

## 원칙 7. 학생의 학교는 방이 정한다 (v4)

학생이 학교를 고르거나 입력하지 않습니다. 방을 만든 선생님의 학교가 곧 학생의 학교입니다.

- 인증 방을 만들 때 방 문서에 `creatorSchool`을 넣습니다. 규칙은 이 값이 **만든 선생님의 학교와 같을 때만** 인증 방을 허락합니다.
- 입장할 때마다 `student_auth.teachers`에 방 선생님 이름을 더합니다 → 학생 관리에 자동으로 쌓입니다.
- 담당 학생이 남은 채 선생님이 학교를 바꾸면 그 학생들이 사라지므로, **정보수정은 담당 학생이 없을 때만 학교를 바꿉니다.**

# 3. 실수 사례집

v2~v4에서 실제로 발견된 것들입니다. **새로 만들 때 같은 자리를 조심하세요.**

## v4 · v4.1에서 고친 것

| 증상 | 원인 | 처리 |
|---|---|---|
| 선생님이 다른 학교 학생 목록을 보고 PIN도 초기화할 수 있음 | v3 규칙이 '승인 교사'면 전부 허락 | 규칙이 '내 학생'(같은 학교 + 담당 이름)만 허락 |
| 기기에서 학번을 바꾸면 이전 학번의 닉네임을 이어받음 | 게임 닉네임만 지우고 방별 닉네임 기억은 남김 | 주인이 바뀌면 모든 게임·방의 닉네임 기억 삭제 |
| PIN을 없앤 v4에서 남의 학번으로 쉽게 입장 | 동시 접속 차단·기기 한도만으로는 부족 | v4.1에서 PIN을 v3 방식 그대로 되살림 |
| PIN 초기화 창에서 다른 학교를 고를 수 있음 | v3 코드를 그대로 되살림 | 선생님은 내 학교로 고정, 관리자만 선택 |
| 한 페이지에서 `room-auth.js`가 두 번 로드될 위험 | 페이지와 game-kit이 서로 다른 `?v=` 주소로 import | 모든 import를 같은 `?v=4.1`로 통일 |

## 치명적이었던 것

| 증상 | 원인 | 교훈 |
|---|---|---|
| 학생 인증 모드 입장이 **항상** 실패 | `freshData` 라는 선언되지 않은 변수. 옵셔널 체이닝(`?.`)은 미선언 변수를 구제하지 못함 | 오타 하나가 기능 전체를 죽입니다. 인증 경로는 반드시 실제 기기로 테스트 |
| 좀비헌터 대시보드에서 교사 세션 탈취 가능 | `onclick="fn('${nick}')"` 에 이스케이프 없이 닉네임 삽입 | 같은 수정을 7개 파일에 복사하면 하나를 놓칩니다 → `game-kit.js` 로 모은 이유 |
| 관리자 계정 탈취 가능 | 교사 등록 시 이름 칸에 스크립트를 넣고, 관리자가 승인 화면을 여는 순간 실행 | 보안 규칙이 자기 승인을 막아도, **관리자 브라우저 안에서 실행되면 우회**됩니다 |
| 게스트가 폰 주인의 닉네임을 이어받음 | 게스트 경로도 "이 기기가 이 방에서 쓰던 이름"을 재사용 | 게스트는 기기의 기억을 **한 줄도** 쓰면 안 됩니다 |
| v1 평문 PIN이 그대로 남아 있음 | v2에서 저장 방식만 바꾸고 기존 데이터를 정리하지 않음 | 저장 구조를 바꾸면 **마이그레이션이 세트**입니다 |

## 조용히 망가져 있던 것

| 증상 | 원인 |
|---|---|
| 교사 PIN 초기화 버튼이 아무 일도 안 함 | 공개 문서의 `pin` 필드를 비웠는데, v2부터 PIN은 그 문서에 없음 |
| 오류가 나도 화면에 아무 반응 없음 | `handleAction` 에 try/catch가 없어 permission-denied가 조용히 사라짐 |
| 게스트 두 번째 입장이 항상 실패 | `guests` 문서에 `create` 만 허용 → 재입장 시 덮어쓰기(update)가 거부 |
| 삭제한 학생이 재등록 불가 | Firestore는 문서를 지워도 하위 컬렉션이 남음. `private/auth` 잔존 |
| PIN 상태가 전원 "재설정 대기" | 공개 문서에 `pin` 필드가 없으니 항상 그렇게 표시 |
| 학교에 교사가 없으면 학생이 목록에서 사라짐 | `teachers: []` 인 학생을 걸러낼 '미지정' 필터가 없었음 |
| RTDB 규칙 배포가 거부됨 | `_comment_*` 키를 최상위에 넣음. RTDB는 `rules` 외 키를 허용하지 않음 |

## 순서를 틀려서 났던 것

| 증상 | 원인 |
|---|---|
| 교사 동기화에서 `permission-denied` | `teacher_directory` 는 새 규칙에만 있는데 규칙 배포 **전에** 실행 |
| v1 PIN 정리가 막힘 | 새 규칙이 `pin` 키가 든 문서의 쓰기를 거부. 정리는 규칙 배포 **전에** 해야 함 |

> **교훈**: 규칙과 코드를 함께 바꿀 때는 어느 쪽을 먼저 올리는지가 중요합니다.
> `DEPLOY.md` 의 순서가 그래서 그렇게 되어 있습니다.

## 실시간 게임에서만 났던 것

| 증상 | 원인 |
|---|---|
| 강퇴한 학생이 유령으로 되살아남 | 하트비트를 일반 `update` 로 처리 → `runTransaction` 으로 "없으면 만들지 않음" |
| 새로고침했더니 경기가 몰수패 | `onDisconnect` 예약을 취소하지 않고 `location.reload()` |
| 교실 전체 매칭이 멈춤 | 탭만 켜 둔 유령이 대기열 맨 앞을 막음 → `alive` 신선도 판정 추가 |
| 두 명이 동시에 매칭을 걸어 한 명이 튕김 | 기기 시계 오차 → `matchLock` 트랜잭션 |
| 점수가 두 번 오름 | 양쪽이 각자 결과를 계산 → `counted`/`statsApplied` 플래그 선점 |

## 고르는 법

**질문 1. 학생끼리 실시간으로 서로 영향을 주나요?**
→ 아니오면 **A**

**질문 2. 짝을 지어 겨루나요, 전체가 하나를 만드나요?**
→ 전체가 하나면 **B**

**질문 3. 누가 무엇을 했는지 기록에 남겨야 하나요?**
→ 예면 **C**, 아니오면 **D**

## C와 D의 차이는 딱 하나

겨루는 방식(대기실·매칭·하트비트·onDisconnect)은 **완전히 같습니다.**
D에서는 학생 인증(학번·PIN)과 게스트 승인만 빠집니다.

그런데 **D도 Firestore를 한 가지 용도로는 씁니다 — 닉네임 중복 방지.**

C·D 모두 플레이어 노드의 '키'가 곧 닉네임입니다.
이름이 겹치면 한 학생이 튕기거나 두 사람 전적이 합쳐집니다.
조합이 3,600개(형용사 60 × 동물 60)라 30명 교실에서 **8번에 한 번꼴로** 겹칩니다.

Firestore는 `create` 전용 규칙으로
> "쓰기에 성공한 사람만 그 이름을 갖는다"

를 만들 수 있습니다. 문서가 이미 있으면 `create`가 실패하니, 읽고 나서 쓰는 사이의
경합이 원천적으로 없습니다. RTDB에는 이 방법이 없습니다.

그래서 이름표만 Firestore에 둡니다.

```
{게임}_records/{방}/nicknames/{닉}   ← 필드가 하나도 없는 빈 문서
```

이름표가 없으면 기기 id 기반 충돌 처리로 버티게 되는데,
"내 기록이 맞나요?" 확인창이 학생에게 뜨는 상황이 생깁니다.

## 유형별 데이터 구조

### 유형 A
```
{게임}_records/{방}              방 문서 (roomMode·createdBy·creatorName·creatorSchool)
  ├ students/{닉}                학번 포함, 교사만 읽음
  ├ nicknames/{닉}               빈 문서
  ├ guests/{닉}                  승인 상태만
  └ records/{자동}               순위표용, 공개 읽기, 학번 금지
```

### 유형 B
```
RTDB rooms/{방}
  ├ title            학생이 읽는 한 칸
  ├ phaseOpen        진행 제어, 교사만 씀
  └ items/{자동}     함께 모으는 내용, 읽기·쓰기 공개
RTDB room_index/{방} 방 목록 전용, 교사만
```

### 유형 C
```
RTDB rooms/{방}
  ├ status           학생이 읽는 한 칸
  ├ players/{닉}     전적·하트비트, 전체 읽기는 교사만
  ├ waiting/{닉}     대기열, 전체 공개 (매칭에 필요)
  ├ matches/{id}     경기, 전체 읽기는 교사만
  └ matchLock        매칭 경합 정리
Firestore {게임}_records/{방}   방 문서(roomMode·creatorSchool) + students · nicknames · guests
```

### 유형 D
```
RTDB       유형 C와 동일
Firestore  {게임}_records/{방}/nicknames  ← 이것만
```

블로토는 매칭 대신 '전원이 같은 라운드를 진행'하는 방식이지만,
학생 정보를 쓰지 않고 이름표만 Firestore에 두는 점이 같아 유형 D로 봅니다.
아직 공개되지 않은 제출값을 `submissions` 노드로 분리한 것도 이 유형의 응용입니다
(원칙 3 참고).

# 8. 보안 규칙 구조

전체는 `rules/firestore-규칙.txt` 에 있습니다. 요점만 적습니다.

## 게임 컬렉션은 패턴으로 걸려 있습니다

```
match /{gameCol}/{roomCode} {
  ...
}
function isGameCol(name) { return name.matches('.*_records'); }
```

**새 게임을 추가해도 규칙을 고칠 필요가 없습니다.**
지금 쓰는 6개: `plus_minus_records`, `multiply_divide_records`, `zombiehunter_records`,
`gomoku_records`, `rps_records`, `blotto_records`

블록 안의 모든 규칙이 `isGameCol(gameCol) &&` 로 묶여 있어,
`teachers` 나 `student_auth` 같은 다른 최상위 컬렉션에는 적용되지 않습니다.

## 하위 컬렉션별 권한 (v4.1)

'내 방' = 방 문서의 `createdBy`가 나(또는 빈 값인 옛 방). 관리자는 모든 방이 내 방입니다.

| 경로 | 학생 | 교사 |
|---|---|---|
| `{방}` | get만 (모드·학교 확인) | 만들기(인증 방은 내 학교만) · **내 방만** 고치기·삭제 |
| `students/{닉}` | 쓰기만 (읽기 불가) | **내 방만** 읽기·삭제 |
| `nicknames/{닉}` | 빈 문서 create만 | 목록 · 내 방 삭제 |
| `guests/{닉}` | get + pending으로만 쓰기 | **내 방만** 승인·거절 |
| `records/{자동}` | 읽기 + 검증된 create | 내 방 삭제 |

## student_auth (v4.1)

'내 학생' = 같은 학교 + `teachers`에 내 이름. 관리자는 모든 학생이 내 학생입니다.

| 할 일 | 학생(로그인 없음) | 교사 |
|---|---|---|
| 한 개 읽기 | 가능 (자기 학번 확인) | 가능 |
| 목록 | 불가 | **내 학생만** — 쿼리에 `school ==` + `teachers array-contains` 필수 |
| 만들기·고치기 | 9개 키, 새 학번 4~5자리, 학교·학번 변경 불가, `presence` 4가지 | 같음 |
| 삭제 · PIN 초기화 | 불가 | **내 학생만** |
| PIN 해시(`private/auth`) 읽기 | 불가 | 불가 |

선생님 본인은 `teachers/{uid}`의 이름을 바꿀 수 없고, `teacher_directory`에는 teachers 문서와 같은 학교·이름만 올라갑니다.
이름이 '내 학생'을 가르는 기준이기 때문입니다.

`school ==`와 `teachers array-contains`를 함께 거는 쿼리는 보통 색인 없이 동작합니다.
"색인이 필요합니다" 오류가 나면 브라우저 콘솔의 링크를 눌러 만들면 됩니다.

## RTDB는 별개입니다

RTDB 규칙은 Firestore를 읽을 수 없습니다.
그래서 각 DB마다 `teacher_uids` 허용 목록을 두고, 승인 시 자동으로 채웁니다.

**RTDB의 `.write` 는 아래로 전파되어 자식 규칙으로 되돌릴 수 없습니다.**
`$nick` 에 `.write: true` 를 주면 그 아래 `score` 를 교사 전용으로 막을 수 없습니다.
`.validate` 로 값의 범위를 묶는 것까지가 한계입니다.

v4.1에서도 RTDB 규칙 4개는 바꾸지 않았습니다. v4.1 코드가 쓰는 경로·필드가 모두 이미 허용되어 있습니다.

| 증상 | 원인 |
|---|---|
| `teacher_directory` 쓰기 거부 | 아직 새 규칙을 배포하지 않음 |
| `teachers` 목록 읽기 거부 | 규칙의 `isAdmin()` uid가 실제와 다름 |
| `student_auth` 쓰기 거부 | 그 문서에 v1 `pin` 필드가 남아 있음 |
| `student_auth` 목록 거부 | 규칙은 v4.1인데 화면이 예전 캐시(쿼리에 담당 선생님 조건 없음) → 강력 새로고침 |

## 학생이 "학교 정보를 찾지 못했습니다"라고 할 때

방을 만든 선생님의 학교명이 없거나 `관리자`입니다. 상단 메뉴 → **정보수정**에서 실제 학교명으로 바꾼 뒤
**방을 새로 만드세요.** (v4.1에서는 학생이 학교를 고르는 드롭다운이 없습니다)

## 선생님이 실시간 게임 방을 못 만들 때

해당 DB의 `teacher_uids` 에 uid가 없습니다.
규칙을 배포한 뒤 **2번**을 실행하세요.

## 학생이 "존재하지 않는 방"이라고 할 때

오목 — 기존 방에 `status` 값이 없습니다. `migrate_v3.html` 의 **3번**으로 채웁니다.

## 대시보드 방 목록이 비었을 때

`teacherAuthChanged` 구독이 빠졌는지 확인하세요.
교사 로그인 결과는 페이지가 뜬 뒤에 도착합니다.

## 학생이 PIN을 잊었을 때

**학생 관리** → 해당 학생 → PIN 초기화, 또는 게임 대시보드 상단 **[PIN 초기화]**(내 학교·내 방 학생만).
학생은 다음 접속 때 새 PIN을 설정합니다.

## 기기를 바꿔 한도(3대)를 넘겼을 때

**학생 관리** 페이지 → 기기 초기화.

## 그 밖의 v4.1 증상

| 증상 | 원인과 조치 |
|---|---|
| 학생 관리에 학생이 안 보임 | 빠른 입장 방이었거나(학번을 받지 않음) 다른 선생님 방 학생입니다. 관리자는 **전체 선생님**으로 확인 |
| 학생 관리 상태가 안 바뀜 | 실시간이 아닙니다. [새로고침]을 누르세요 (기준 시각은 버튼 아래) |
| 학생 관리: "학생 정보를 불러오지 못했습니다" | 규칙은 v4.1인데 화면이 예전 캐시 → 강력 새로고침. 콘솔에 색인 링크가 보이면 눌러 색인 생성 |
| 정보수정: "담당 학생 N명이 있어 학교를 바꿀 수 없습니다" | 의도된 제한. 학생을 삭제하거나 담당 선생님에서 빼면 바꿀 수 있습니다 |
| 인증 방 만들기 실패 | 규칙이 `creatorSchool` ≠ 내 학교면 거부합니다. 정보수정의 학교명 확인 후 새로고침 |
| 학생: "보안 연결 필요" | https가 아닌 주소(file:// 등)로 열었습니다. 배포 주소로 여세요 |
| 다른 학생이 내 학번으로 들어옴 | PIN이 샌 것입니다. **PIN 초기화 + 기기 초기화** 후 본인이 새 PIN으로 입장 |

# 10. 알고 쓰셔야 하는 한계

학생에게 로그인이 없으므로, 아래는 규칙만으로 막을 수 없습니다.
**수업 진행에는 지장이 없는 수준**이라 그대로 두었습니다.

1. 콘솔에서 다른 닉네임의 기록을 덮어쓰는 것
2. 자기 점수나 승수를 직접 올리는 것 (값의 범위는 제한했습니다)
3. 아직 등록하지 않은 학번의 PIN을 남이 먼저 만들어 두는 것
   → 선생님이 **학생 관리 → PIN 초기화**로 풀어주시면 됩니다
4. 남이 쓸 닉네임을 미리 차지하는 것
5. 4자리 PIN 전수 대입 — PBKDF2 10만 회로 비싸게 만들 뿐 막지는 못합니다
6. 같은 학교에 같은 이름의 선생님이 둘이면 서로의 학생이 보입니다 ('내 학생'을 이름으로 가르기 때문)
7. '담당 학생이 있으면 학교 변경 금지'는 규칙으로 셀 수 없어 정보수정 화면에서만 막습니다

## App Check가 막는 것과 못 막는 것

- ✅ 페이지 밖에서 오는 요청 (curl, 외부 스크립트)
- ❌ **학생이 F12로 페이지 안에서 호출하는 것**

App Check는 보안 규칙을 대체하지 않습니다.
콘솔에서 "적용(Enforce)"까지 눌러야 효과가 있고, RTDB는 4개 인스턴스 각각 확인해야 합니다.

## 근본 해결책

**Firebase 익명 인증**입니다.
학생도 uid를 갖게 되면 `players/{닉}.uid == auth.uid` 같은 소유권 규칙을 쓸 수 있어
위 네 가지가 모두 막힙니다.

- 학생 화면에는 아무 변화가 없습니다 (로그인 창이 뜨지 않습니다)
- `signInAnonymously(auth)` 한 줄 + 규칙 수정
- 지금 구조 위에 나중에 얹을 수 있습니다

여유가 생기면 다음 단계로 고려해보세요.

# 11. 학생 관리 페이지

## 누가 무엇을 보나

| | 학교 | 담당 선생님 |
|---|---|---|
| 선생님 | 내 학교로 고정 | 내 이름으로 고정 — **내 방에 들어온 학생만** (게스트 포함) |
| 관리자 | 골라서 봄 | 한 명씩 고르거나 **전체 선생님** |

'담당 미지정' 필터는 없습니다. 기기를 등록하는 순간 방 선생님이 담당 선생님이 되기 때문입니다.
담당 선생님이 비어 있는 예전 학생은 관리자가 **전체 선생님**으로 봅니다.

## 할 수 있는 일

PIN 초기화 · 기기 초기화 · 접속 해제 · 담당 선생님 수정 · 삭제 (개별·일괄). PIN 열에는 설정됨 / 재설정 대기가 보입니다.
삭제하면 PIN 해시(`private/auth`)까지 지워, 그 학번은 다음 입장 때 새로 등록됩니다.

## 접속 상태

좌표평면 오목과 같은 색입니다. 표는 상태 순(접속중이 위), 같은 상태 안에서는 학번 순입니다.

| 표시 | 뜻 |
|---|---|
| 🟢 접속중 | 게임 화면을 보고 있음 (120초 안에 신호) |
| 🟡 다른화면 | 게임 탭을 떠나 다른 탭·앱을 보는 중 |
| 🔵 승인 대기 | 게스트가 선생님 승인을 기다리는 중 |
| 🔴 접속 끊김 | 30분 안에 신호가 끊김 (창을 정상적으로 닫지 않음·네트워크) |
| ⚪ 미접속 | 정상적으로 나갔거나 마지막 신호가 30분보다 오래됨 |

**실시간이 아닙니다.** 서버에서 읽는 것은 페이지를 열 때, 학교를 바꿀 때, **[새로고침]**을 누를 때뿐이고,
상태는 그 시각 기준입니다. 버튼으로 한 작업은 서버에 쓰고 화면에만 바로 반영합니다.

## 선생님 학교 변경

담당 학생이 한 명이라도 있으면 정보수정에서 학교를 바꿀 수 없습니다.
학생 관리에서 학생을 삭제하거나 담당 선생님에서 뺀 뒤 바꾸세요.
