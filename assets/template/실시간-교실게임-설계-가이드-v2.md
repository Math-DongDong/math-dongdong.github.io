# 실시간 교실 게임 설계 가이드 v3

> Firebase(RTDB + Firestore) + 순수 JS(서버 없음)로 만든 교실용 게임을
> 실제 수업에서 운영하며 겪은 사고를 고친 결과를 정리한 기준서입니다.
>
> **v2 → v3에서 달라진 것**: v2는 "게임 한 판이 어떻게 안 깨지는가"까지였습니다.
> v3는 그 위에 얹힌 **신원 계층**을 포함합니다 — 교사 로그인·승인, 방 모드(빠른 입장 / 학생 인증),
> 학번·PIN·기기 등록, 게스트(공용기기) 승인, **닉네임 입력창 폐지와 자동 닉네임**,
> 방 소유권, QR 입장. 게임 로직보다 이쪽에서 사고가 더 많이 났습니다.

- **대상 환경**: Firebase RTDB(실시간) + Firestore(기록·신원) + 클라이언트 전용
- **사용 상황**: 교실 20~35명 동시 접속, 크롬북·태블릿·개인 스마트폰 혼재, 학교 와이파이
- **함께 쓰는 파일**

| 파일 | 역할 |
|---|---|
| `realtime-matching.html` | 1:1 자동 매칭 게임 뼈대 (8~13장 구현체) |
| `realtime-basic.html` | 매칭 없는 게임 뼈대 (14장 구현체) |
| `stage-basic.html` | 스테이지형 학습게임 뼈대 — 기록형·Firestore (21장 구현체) |
| `js/navbar.js` | 통합 네비게이션 + 교사 인증 모듈 자동 로드 |
| `js/teacher-auth.js` | 교사 Google 로그인·등록·승인 상태 관리 (3장) |
| `js/room-auth.js` | 첫화면 카드·모달·자동 닉네임·학생 인증·게스트 (4·16장) |
| `js/dashboard-header.js` | 대시보드 상단(방 선택·생성·삭제·엑셀·PIN 초기화) + QR 자동 로드 |
| `js/qr-modal.js` | 방 입장 QR 플로팅 패널 (15.5) |
| 이 문서 | 위 코드가 **왜** 그렇게 생겼는지 + 함정 대사전 |

**설계 원칙 4줄 요약** (v2의 3줄 + 신원 계층 1줄)

1. 여러 클라이언트가 동시에 실행해도 되는 코드로 짜되, **딱 한 명만 성공하는 관문**(트랜잭션)을 통과시킨다.
2. 상태 변경은 **여러 경로를 한 번의 `update()`로** 묶어 원자적으로 처리한다.
3. 시간 판정은 `Date.now()`가 아니라 **서버 보정 시각**으로 한다.
4. **신원은 학생이 입력하지 않는다.** 화면에 뜨는 이름은 자동 발급하고, 진짜 신원(학번)은 인증 모드에서만 따로 받는다.

## 1. 세 가지 게임 계열

새 게임을 기획하면 먼저 계열부터 정한다. 이후의 모든 결정이 여기서 갈린다.

| | **기본형** | **매칭형** | **기록형(스테이지)** |
|---|---|---|---|
| 템플릿 | `realtime-basic` | `realtime-matching` | `stage-basic` |
| DB | RTDB | RTDB | **Firestore** |
| 구조 | 각자 진행, 교사가 전체 관찰 | 대기실 → 1:1 대전 → 복귀 | 개인 스테이지 진행 + 성취 기록 |
| 예시 | 블로토 | 가위바위보, 좌표평면 오목 | 좀비헌터 |
| 필요한 층 | 세션 + 하트비트 + 대시보드 | + 대기열 + 매칭 + 경기 수명주기 | 세션·하트비트 **전부 불필요** |
| 난이도 | 경합 지점이 적음 | 경합 지점이 설계의 전부 | 출제 정합성과 저장 시점이 전부 |

**세 계열이 공유하는 것**(2~5·15~19장)은 완전히 동일하다: 네비게이션, 교사 인증, 첫화면, 자동 닉네임, 방 소유권, 대시보드 서식, QR 입장, 보안 규칙 골격.

```
[공통]   네비 → 교사 로그인 → 첫화면(방 코드) → 신원 결정 → (게임) → 대시보드 관찰
[매칭형] 위 + 대기실 등록 → 매칭 6단계 → 포인터 진입 → 경기 → 정산 → 복귀
[기록형] 위 + 스테이지 진행 → 두 시점 저장 → 성취 대시보드
```

## 2. 공통 인프라 지도

게임 페이지가 직접 만드는 UI는 **게임 화면뿐**이다. 나머지는 전부 공통 모듈이 삽입한다.
새 게임을 만들 때 "이건 내가 만들어야 하나?"를 여기서 먼저 확인한다.

| 모듈 | 자동으로 만들어 주는 것 | 게임 페이지가 할 일 |
|---|---|---|
| `navbar.js` | 상단 네비, 로고, 메뉴, `#teacher-auth-container` | `<div id="navbar-placeholder">` + 스크립트 한 줄. 메뉴 항목은 `NAVBAR_DATA`에 추가 |
| `teacher-auth.js` | 교사 로그인 버튼/드롭다운, 등록·정보수정 모달, 전역 상태, `teacherAuthChanged` 이벤트 | 이벤트를 듣고 방 목록 재로딩 |
| `room-auth.js` | 방 입장 카드, 공통 모달, 게임방법 슬라이드, 자동 닉네임, 학생 인증·게스트 흐름 | `renderRoomEntrance(컨테이너, 옵션)` 한 번 호출 |
| `dashboard-header.js` | 제목, 방 선택 `<select>`, 새 방 만들기, 방 삭제, 엑셀, PIN 초기화 | 생성된 id에 이벤트만 연결 |
| `qr-modal.js` | 방 입장 QR 플로팅 패널 (드래그·리사이즈·위치 기억) | **없음** (dashboard-header가 자동 로드) |
| `dashboard.css` | 대시보드 헤더 반응형 그리드, `.section-container` 전환, 카드 서식 | 클래스만 사용 |

### 2.1 로드 순서와 경로 계산

`navbar.js`는 `location.pathname`에서 `pages` 세그먼트를 찾아 루트 상대경로를 스스로 계산한다.
`pages/middleschool/1/xxx.html`이면 `../../../`. 그래서 **페이지 깊이가 달라도 스크립트 경로만 맞으면 된다.**

- `data-type="aimath|automation|middleschool"`로 메뉴 그룹을 지정할 수 있고, 없으면 경로로 자동 판정한다.
- `data-no-render="true"`는 메뉴 데이터(`window.NAVBAR_DATA`)만 쓰고 네비바는 안 그린다(메인 페이지 전용).
- 네비바가 그려진 뒤 `teacher-auth.js`를 **모듈로 동적 로드**한다. 즉 모든 게임 페이지에 교사 로그인이 자동으로 붙는다.

### 2.2 로드 순서가 만드는 함정

교사 로그인 결과는 **비동기로 나중에** 도착한다. 페이지가 뜬 직후 `window.isAdmin`은 항상 `false`다.
그래서 대시보드 관련 초기화는 반드시 두 경로 모두에서 실행해야 한다.

```js
// ① 대시보드에 들어갈 때
onAdminSuccess: () => { showSection('admin-section'); loadRooms(); }
// ② 로그인/승인 상태가 나중에 바뀔 때
window.addEventListener('teacherAuthChanged', () => loadRooms());
```

`teacher-auth.js`는 추가로 `[300, 800, 1500, 3000]ms`에 `updateDashboardButtons()`를 재실행해
동적으로 삽입된 `#btnOpenDashboard`를 뒤늦게 찾아낸다. 대시보드 버튼을 직접 만들었다면
id를 `btnOpenDashboard` 또는 `btn-admin-dash`로 맞춰야 이 보정이 걸린다.

## 3. 교사 인증 계층

### 3.1 상태 기계

```
로그아웃                     → [교사 로그인] 버튼 (Google 팝업)
로그인 & teachers/{uid} 없음 → 등록 모달(학교명·이름) → status:'pending'
                              취소하면 deleteUser()로 계정 자체를 제거 (유령 계정 방지)
status:'pending'            → "승인 대기 중" 배지 + 로그아웃
status:'approved'           → "OOO 선생님" 드롭다운 (학생 관리·정보수정·로그아웃)
email === ADMIN_EMAIL       → 자동 approved + "관리자 접속" 드롭다운 + 승인 대기 알림
```

전역 상태 6개가 이 결과를 게임 페이지에 전달한다.

```js
window.isApprovedTeacher   // 승인된 교사인가 (관리자 포함)
window.isAdmin             // 관리자인가
window.currentTeacherUid   // 방 소유권 기록용
window.currentTeacherEmail // uid가 바뀌어도 소유권을 잃지 않게 하는 보조 키
window.currentTeacherName  // 방 문서에 남길 표시 이름
window.currentTeacherSchool
```

### 3.2 게임 페이지가 지켜야 할 소유권 3규칙

교사가 여러 명 쓰는 사이트에서 **남의 방이 내 드롭다운에 보이면 그날 수업이 엉킨다.** 세 곳을 고정한다.

**① 방을 만들 때 소유자를 기록한다**

```js
await setDoc(roomDocRef(code), {
    roomCode: code,
    createdAt: serverTimestamp(),
    createdBy:    window.currentTeacherUid   || '',
    creatorEmail: window.currentTeacherEmail || '',
    creatorName:  window.currentTeacherName  || ''
});
```

**② 목록은 관리자가 아니면 내 방만**

```js
if (!window.isAdmin) {
    if (data.createdBy !== window.currentTeacherUid &&
        data.creatorEmail !== window.currentTeacherEmail) return;   // 건너뜀
}
```
`uid`와 `email`을 **둘 다** 보는 이유: 계정을 지웠다 다시 만들면 uid가 바뀐다. 이메일이 예비 열쇠다.
필터 결과가 0건이면 빈 드롭다운 대신 `생성한 방이 없습니다 (새 방을 만드세요)`를 넣는다 —
빈 목록은 "고장"으로 오해받는다.

**③ 삭제는 소유자 확인 후**

```js
if (!window.isAdmin && rData.createdBy && rData.createdBy !== window.currentTeacherUid) {
    return customAlert("권한 없음", "직접 생성한 방만 삭제할 수 있습니다.");
}
```
`rData.createdBy &&` 조건이 중요하다. 소유권 필드가 없던 **옛 방**은 아무도 못 지우게 되면 곤란하다.

### 3.3 학교·교사 목록의 출처

학생 인증 화면의 학교 드롭다운과 담당 교사 체크박스는 **`teachers` 컬렉션에서 실시간으로 만든다**
(`fetchApprovedTeachers` → `fetchSchoolList` / `fetchTeacherNames`, `status == 'approved'`만).

- 학교명이 `'관리자'`인 문서는 목록에서 제외된다. 관리자 계정으로 학생 화면을 테스트하면
  본인 학교가 안 보이는데, 이건 버그가 아니라 의도다. 실제 학교명으로 바꾸면 나타난다.
- 목록은 **세션 내 1회 캐시**된다. 교사가 정보를 수정하면 `window.clearTeacherCache()`를 불러
  캐시를 비워야 학생 화면에 즉시 반영된다.
- 승인된 교사가 한 명도 없는 학교면 "등록된 선생님이 없습니다. 그대로 진행해도 됩니다"로
  안내하고 통과시킨다. 여기서 막으면 학기 초에 아무도 입장하지 못한다.

## 4. 학생 신원 계층 — 방 모드·자동 닉네임·게스트

### 4.1 방을 만들 때 모드를 고른다

```js
const mode = await promptRoomMode();   // 'quick' | 'auth' | null(취소)
await setDoc(roomDocRef(code), { roomMode: mode, settings: { mode }, ... });
```

| | **A. 빠른 입장** (`quick`) | **B. 학생 인증** (`auth`) |
|---|---|---|
| 학생이 입력하는 것 | 방 코드 4자리 **뿐** | 방 코드 + (최초 1회) 학교·담당교사·학번·PIN |
| 화면 이름 | 자동 닉네임 | 자동 닉네임 (학번은 대시보드에서만) |
| 기록에 학번 | 없음 | 있음 |
| 공용 기기 | 그냥 씀 | 게스트 모드(교사 승인 필요) |
| 쓰는 때 | 1회성 활동, 저학년, 개인정보 최소화 | 성취 평가·누적 기록이 필요한 수업 |

`roomMode`와 `settings.mode`에 **같은 값을 두 번 쓴다.** 옛 방과 새 코드가 섞여도 한쪽만 보면 되도록 한
하위호환 장치이고, 읽을 때는 `roomData?.roomMode || roomData?.settings?.mode || 'quick'`로 폴백한다.
**모드를 모르면 항상 `quick`** — 안전한 쪽이 기본값이다.

### 4.2 닉네임 입력창을 없앤 이유

v2까지는 학생이 닉네임을 직접 입력했다. 실제로 일어난 일:

- 오타·비속어·다른 학생 이름 사칭, 그리고 **실명 입력**(개인정보가 대시보드와 명예의 전당에 그대로 노출)
- `. # $ [ ] /`·제어문자가 RTDB 키를 깨뜨림
- 같은 학생이 게임마다 다른 이름을 써서 누적 기록이 이어지지 않음

그래서 **화면 이름은 시스템이 발급한다.** 형용사 60개 × 동물/캐릭터 60개 = 3,600개 조합
(`generateRandomNickname()` → `"부끄러운 어피치"`).

### 4.3 닉네임은 "게임별로" 고정된다

기준은 페이지 경로다.

```js
gameKey()  // location.pathname → 영숫자만 남기고 정규화, 뒤 60자
```

| 순위 | 출처 | 언제 |
|---|---|---|
| 1 | `student_auth/{key}.nicknames[gameKey]` | 인증 모드. **다른 기기에서도 같은 이름** |
| 2 | `localStorage['gameNickname:' + gameKey]` | 이 기기에서 이미 쓰던 이름 |
| 3 | 새로 발급 | 이 게임 첫 입장 |

- 배정 시점은 **"방 코드를 넣고 입장하는 순간"**이다. 첫화면을 열기만 해서는 배정되지 않는다.
- 같은 게임에 다시 들어오면 계속 같은 이름 → 누적 기록·명예의 전당이 이어진다.
- 다른 게임에서는 다른 이름 → 게임 간 추적을 막는다.
- 사생활 보호 모드처럼 `localStorage`가 막힌 환경을 위해 **메모리 폴백**(`_memNickname`)이 있다.
  그 세션 동안만 유지된다.

게임 쪽에서 이름이 최종 확정되면(중복 회피 등) 반드시 되돌려 저장한다.

```js
if (finalName !== name) await saveGameNickname(finalName, authInfo);
```

### 4.4 닉네임 길이 상한은 10자가 아니라 **12자**

자동 닉네임은 최대 `형용사 4자 + 공백 1 + 동물 4자 = 9자`다. 그런데 충돌 폴백이 접미사를 붙인다.

- `room-auth`의 `generateUniqueNickname` 최후 폴백: `+2자` → **11자**
- 게임 쪽 재발급 폴백 `${name}_${두자리}`: `+3자` → **12자**

v2 템플릿의 `NICKNAME_RE = /^[...]{1,10}$/`를 그대로 두면 **충돌이 난 학생만 입장을 거부당한다.**
드물게 터지고 재현이 안 돼서 진단이 어렵다. 상한을 **12자**로 맞춘다.

```js
const NICKNAME_RE = /^[가-힣a-zA-Z0-9_\- ]{1,12}$/;   // 자동 발급 9자 + 충돌 접미사 3자
```

### 4.5 인증 모드 흐름 (본인 기기)

```
입장 버튼
 └─ 저장된 폰 주인 정보(localStorage) 있음?
     ├─ 없음 → 인증 모달(학교·담당교사·학번·PIN)
     └─ 있음 → student_auth 조회
          ├─ 문서 없음(교사가 삭제)      → 재등록 모달
          ├─ 저장 PIN ≠ 서버 PIN(딴 기기서 변경) → 재인증 모달
          └─ 일치 → "내 정보가 맞나요?" 확인 모달 → [맞아요] / [정보 수정]
 └─ 서버 PIN이 null(교사가 초기화)  → 새 PIN 설정 모달
 └─ 기기 등록 (최대 3대, 초과 시 차단하고 교사에게 초기화 요청 안내)
 └─ 닉네임 결정(4.3) → 방의 students 문서 생성 → onJoin
```

**학번 탈취 방지 3중 장치** (정보 수정 시 다른 학생 학번을 입력하는 경우)

1. 대상 계정이 **접속 중**이면 변경 불가 — `isAccountOnline()`: `presence === 'online'` **그리고**
   `lastActive`가 90초 이내. status 하나만 믿으면 조용히 끊긴 계정이 영원히 잠긴다.
2. 이미 등록된 학번이면 **PIN이 일치해야만** 사용 가능.
3. **기존 PIN은 클라이언트가 절대 덮어쓰지 않는다.** 초기화는 교사만(`showPinResetModal`).
   `pin: null`인 계정에서만 새 PIN을 기록한다.

검증에 실패하면 `continue`로 **모달을 다시 띄운다.** 한 번 틀렸다고 첫화면으로 되돌리면
학생은 무엇이 틀렸는지 모른 채 같은 실수를 반복한다.

### 4.6 게스트 모드 — 공용 기기의 두 저장소

교실 태블릿처럼 기기를 돌려 쓰는 경우, **폰 주인의 정보를 게스트가 덮으면 안 된다.**
저장소를 물리적으로 분리해서 해결한다.

| 대상 | 저장소 | 키 | 수명 |
|---|---|---|---|
| 폰 주인 | `localStorage` | `studentAuth:*` | 영구 |
| 게스트 | `sessionStorage` | `guestAuth:*` | 탭을 닫으면 소멸 |

> **규칙**: 게스트 경로의 코드는 `localStorage`를 **읽지도 쓰지도 않는다.**
> 예외를 한 번 만들면 반드시 앞 학생 계정을 덮는다.

승인 흐름:

```
게스트 스위치 ON + 입장
 → 폰 주인 계정을 presence:'offline'로 내림
 → 게스트 인증 모달 → student_auth 확인/생성 (devices: [] — 공용기기는 기기 등록 안 함)
 → students/{닉}.status = 'pending' + 대기 스피너 모달
 → 교사 대시보드 상단에 승인 배너 → [승인 허용] → status:'online'
 → onSnapshot이 감지 → 게임 진입 + 우측 상단 [게스트 모드 종료] 버튼 상시 노출
 → 종료 시 게스트 정보 파기 + 폰 주인 계정 presence:'online' 복구 + reload
```

**게스트 승인은 Firestore `students` 컬렉션이 있어야 동작한다.** `renderRoomEntrance`에
`studentsCollectionRef`를 넘기지 않으면 승인 대기 모달이 영원히 안 닫힌다.
그래서 **RTDB 전용 게임(기본형·매칭형)은 현재 `quick` 모드만 지원**한다 — 방을 만들 때
`roomMode: 'quick'`을 고정으로 기록한다. 인증 모드가 꼭 필요하면 방/학생 문서만 Firestore에 따로 두고
`studentsCollectionRef`를 넘기면 된다(21장 기록형이 그 형태다).

> 알려진 거친 모서리: 게스트 스위치는 `quick` 방에서도 화면에 보이지만 무시된다.
> 방 모드를 미리 알 수 없어(코드 입력 전) 숨기지 못한 것으로, 혼란이 관찰되면
> `getRoomData` 응답 후 스위치를 비활성화하는 쪽으로 고친다.

### 4.7 `authInfo` — 게임에 전달되는 신원 꾸러미

`onJoin(roomCode, nickname, authInfo)`의 세 번째 인자다. **게임 로직의 분기는 전부 이 객체로 한다.**

| 필드 | 값 | 의미 |
|---|---|---|
| `mode` | `'quick'` \| `'auth'` | 방 모드 |
| `isGuest` | boolean | 공용기기 게스트인가 |
| `school` | string \| `''` | 인증 모드에서만 |
| `studentId` | string \| `''` | 인증 모드에서만 |
| `nicknameFixed` | boolean | **이미 고정된 이름인가** |

`nicknameFixed`가 v3의 핵심 최적화다. 이 값이 `true`면 그 이름은 이미 서버에 기록돼 있으므로
게임이 다시 중복 검사를 할 필요가 없다. `false`(= 방금 처음 발급)일 때만 무거운 검사를 돌린다.

```js
const isAuthMode = authInfo?.mode === 'auth';
if (!isAuthMode && !authInfo?.nicknameFixed) {
    /* 전 방 순회 중복 검사 → 겹치면 재발급 → saveGameNickname */
}
```
인증 모드에서 이름을 바꾸면 **안 된다.** room-auth가 이미 `student_auth`와 방의 `students` 문서를
그 이름으로 만들어 뒀기 때문에, 게임이 여기서 이름을 갈면 기록이 두 갈래로 쪼개진다.

## 6. 기반 장치 — 서버 시간·하트비트·onDisconnect

> 기록형(21장)에는 이 장이 통째로 필요 없다.

### 6.1 서버 시간 동기화

```js
let serverOffset = 0;
onValue(ref(db, '.info/serverTimeOffset'), s => serverOffset = s.val() || 0);
const serverNow = () => Date.now() + serverOffset;
```
DB **기록**은 가능하면 `serverTimestamp()` 센티널. 단 **트랜잭션 안에서는 센티널이 해석되지 않으므로**
`serverNow()` 값을 직접 쓴다. Firestore **배열 필드 안**도 마찬가지다(`devices`가 `Date.now()`를 쓰는 이유).

### 6.2 하트비트 — 반드시 트랜잭션으로

```js
async function updateHeartbeat() {
    if (!currentRoomCode || !currentNickname || isKicked || isTeacher) return;
    await runTransaction(playerRef(room, me), (cur) => {
        if (cur === null) return;              // ★ 삭제(강퇴)됨 → 부활 금지
        cur.lastHeartbeat = serverNow();
        cur.status = document.hidden ? 'away' : 'online';
        return cur;
    });
    if (대기실화면) update(waitingRef(room, me), { alive: serverTimestamp() });
}
```
단순 `update()`가 터뜨린 사고 둘: ① 강퇴된 학생의 낡은 클라이언트가 3초 뒤 유령 노드를 되살림,
② 교사가 방을 삭제한 직후 학생 하트비트가 **삭제된 방을 부분 부활**시킴.

### 6.3 onDisconnect 3종과 "해제 규율"

| 대상 | 예약 내용 | 막는 사고 |
|---|---|---|
| `players/{me}` | `{status:'offline', currentMatchId:null}` | 유령 접속자 잔류 |
| `waiting/{me}` | `remove()` | 사라진 학생이 1순위로 남아 **대기실 전체 잠김** |
| `matches/{id}` | `{status:'finished', winner, endReason:'offline'}` | 상대가 빈 화면을 무한 대기 |

**예약보다 중요한 것이 해제다.**

- 경기가 정상 종료됐는데 `cancel()`을 안 함 → 나중에 브라우저를 닫는 순간 **끝난 경기가 몰수로 덮어써짐**.
  → 경기가 끝나는 **모든** 경로에서 `disarmMatchDisconnect()`.
- 중복 접속으로 물러나는 기기가 예약을 안 지운 채 `location.reload()` → reload는 연결 종료이므로
  예약이 발동해 **새 기기의 상태를 offline으로 덮음**. → `cleanupAll()` 첫 줄에서 예약 3종 전부 취소.
- 물러나는 기기가 `waiting/{me}`를 **직접 삭제**하면 그건 새 기기의 항목이다.
  → 정리 시에는 구독·예약만 해제(`cleanupWaiting(false)`).

한계: **다른 연결의 예약은 취소할 수 없다**(12.4).

## 7. 세션 관리

```
입장 시  localSessionId = Date.now() + 랜덤4자
        update(players/{me}, { sessionId: localSessionId, ... })

상시    unsubMe = onValue(players/{me}, snap => {
            if (!snap.exists())          → 강퇴/삭제 → cleanupAll() → 안내 → reload
            if (snap.sessionId ≠ 내 것) → 인수당함 → cleanupAll() → 안내 → reload
        })
```

- **`isKicked`**: 물러난 세션의 하트비트·매칭·쓰기를 전부 가드.
- **`sessionEnded`**: 방 삭제 감지와 세션 감지가 동시에 울려 모달이 두 번 뜨는 것 방지.
- **`cleanupAll()`은 reload 직전에 반드시**.
- 교사(`isTeacher`)는 이 감시에서 제외 — 교사는 player 노드가 없다.

중복 접속을 **차단이 아니라 인수**로 처리하는 이유는 12.2(자기 유령 문제).

## 8. 매칭 6단계

```
① 활성 대기자 필터  : visible === true && (now − alive) < 25초
② 리더 선출        : ts가 가장 이른 활성 대기자 == 나 (아니면 즉시 return)
③ 상대 선택        : 직전 상대 양방향 회피 → 대안 없으면 즉시 폴백 → 무작위(또는 선입)
④ matchLock 선점   : 트랜잭션, TTL 3초 (실패는 정상 — 조용히 return)
⑤ 재확인          : 서버에서 waiting을 새로 읽어 양쪽 잔류 확인
⑥ 원자적 성사      : 단일 update()로 경기 생성 + 포인터 + lastOpponent
                     + 대기열 제거 + 잠금 해제를 전부 한 번에
```

**① visible과 alive는 보완 관계다.** visible만 쓰면 탭이 켜진 채 와이파이가 끊긴 학생이
**대기열 맨 앞을 영구 점거**한다. onDisconnect의 waiting 삭제는 서버가 죽은 연결을 감지할 때까지
수십 초 걸린다. alive 신선도(하트비트×2.5 = 25초)가 이 유령을 자동 탈락시킨다.
반대로 alive만 쓰면 앱을 전환한 학생이 최대 10초간 후보로 남는다.

**② 리더 선출만으로는 부족하다.** 두 클라이언트가 서로 다른 스냅샷을 보면 둘 다 리더라고 믿는다. ④가 최종 방어선.

**③ 폴백은 필수다.** 대기자가 2명뿐이고 서로 직전 상대이면 폴백 없이는 영원히 매칭되지 않는다.
양방향 확인(`후보 ≠ 내 직전상대 && 나 ≠ 후보의 last`)이 한쪽만 기억하는 비대칭을 막는다.

**④ 잠금의 3원칙.** 중단은 `return;`(undefined), 승패는 `res.committed`.
**TTL이 없으면 잠금 보유자가 죽는 순간 방 전체가 영구 동결**된다.

**⑤ 재확인은 캐시가 아니라 서버 `get()`으로.**

**⑥ 쪼개면 안 된다.** 나누면 "경기는 생겼는데 대기열에 남은 학생", "반쪽 매칭"이 생긴다.

```js
async function attemptMatch() {
    if (currentMatchId || isMatching || isKicked) return;   // 재진입 가드
    isMatching = true;
    let lockHeld = false;
    try { /* ①~⑥ */ }
    finally {
        isMatching = false;
        if (lockHeld) await set(matchLockRef(room), null).catch(() => {});
    }
}
```
**트리거는 이벤트 + 저빈도 폴링 병행**: waiting `onValue` + `setInterval(attemptMatch, 1500)`.

## 9. 경기 진입 3중 안전망

```
[안전망 1] 포인터 전용 구독 (주 방어선)
    onValue(players/{me}/currentMatchId) → 경기 1건만 get → 검증 → enterGame
    · 검증 3종: status==='playing' / 내가 참가자 / currentMatchId 미중복
[안전망 2] 매칭 루프 앞머리의 서버 확인
    attemptMatch() 첫 줄 resolveMyMatch() — 포인터를 항상 서버 get으로
[안전망 3] 1.5초 폴링 — 스냅샷 유실·구독 순단까지 회복
```

세 경로가 전부 **`enterGame(mid, m)` 하나로 수렴**하고, 첫 줄 `if (currentMatchId) return;`이 중복 진입을 막는다.
대기실에 **들어갈 때마다 포인터를 null로 초기화**해야 끝난 옛 경기로 되돌아가지 않는다.

## 10. 경기 종료·정산 — 멱등성

**종료 확정**과 **전적 반영**을 분리하고, 각각 트랜잭션으로 1회만 성공하게 한다.

```js
async function finishMatchAtomic(matchId, winnerId, reason) {
    const res = await runTransaction(matchRef(room, matchId), (cur) => {
        if (!cur || cur.status !== 'playing') return;   // 이미 끝남 → 중단
        cur.status = 'finished';
        cur.winner = winnerId || null;                  // null = 무효 (승패 미기록)
        cur.endReason = reason;
        return cur;
    });
    return res.committed;
}
```
호출 주체: 승리 판정 / 본인 이탈 / 상대 감시 / 정체 감지 / 수동 취소 / 강퇴 / onDisconnect / 재접속 정리.

```js
async function settleMatch(matchId, data) {
    if (!data || data.status !== 'finished' || data.statsApplied) return;
    const res = await runTransaction(ref(db, `.../matches/${matchId}/statsApplied`),
        (cur) => (cur === true ? undefined : true));
    if (!res.committed) return;                          // 도장은 1명만

    const winnerValid = data.winner && (data.winner === data.p1 || data.winner === data.p2);
    for (const nick of [data.p1, data.p2]) {
        const pRef = playerRef(room, nick);
        if (!(await get(pRef)).exists()) continue;       // ★ 강퇴된 노드 부활 금지
        const patch = { currentOpponent: null };
        if (winnerValid) patch[nick === data.winner ? 'wins' : 'losses'] = increment(1);
        await update(pRef, patch);
    }
}
```

- **`increment()`를 쓰는 이유**: `runTransaction`은 로컬 캐시가 없으면 첫 콜백에 `null`을 넘긴다.
  무심코 `return {wins:1}` 하면 기존 전적이 통째로 덮인다.
- **`get()` 존재 확인**: 정산과 강퇴가 겹치면 삭제된 학생이 유령으로 부활한다.
- **개인 도장 대안**(`matches/{id}/counted/{me}`): 판이 짧고 상대가 이미 떠났어도 내 기록은 남겨야 하는
  게임(가위바위보)에 맞다. 제3자가 결과를 확정하는 게임은 공용 도장이 맞다. 템플릿은 공용 도장.

종료 후: 복귀 시 포인터를 null로, **양쪽 모두 떠난 경기는 `matches/{id}`를 삭제**.

## 11. 이탈·정체·탈출 — 4중 방어

| 층 | 감지 주체 | 잡는 것 | 지연 |
|---|---|---|---|
| 1. match onDisconnect | 서버 | 브라우저 종료·단절 (양쪽 동시 종료 포함) | 즉시~수십 초 |
| 2. 상대 감시 | 상대 클라이언트 | 조용한 끊김·장기 away | AFK 한계 |
| 3. visibility 유예 → 자진 처리 | 본인 | 앱 전환·화면 잠금 후 미복귀 | GRACE 후 |
| 4. 정체 감지 + 탈출 버튼 | 상대/본인 | **상대가 살아 있는데 경기에 못 들어온 경우** | STALL 후 |

층 1~3은 전부 "상대가 죽었는가"를 본다. 실제 사고는 상대가 **멀쩡히 대기실 화면을 보고 있어서**
(매칭 성사를 놓침) 하트비트가 계속 신선한 경우였다.

- **정체 감지**: 한 수도 없이 (탈출버튼 시간 + STALL) 경과 → `endReason:'error'`, **승패 없이** 복귀.
- **탈출 버튼**: 첫 행동 전 40초 뒤 노출, 클릭 시 `abandoned`. **한 수라도 두어지면 영구 숨김**.

상대 감시 3원칙: ① `opponentSynced` 가드 ② 하트비트 **값의 변화 시각을 로컬로** 기록
③ 판정 즉시 구독 해제. 유예(GRACE)는 판 길이의 30~50%.

## 12. 재접속 로직

**입장 코드는 첫 입장과 재접속을 구분하지 않는다.**

```
① 노드 판독      isComplete(필수 필드 온전)? 아니면 '새로 생성'으로 복구
② 중복/유령 판정  looksOnline = status≠offline && (now−hb) < 40초
                 → 참이면 하드 차단이 아니라 customConfirm("이어서 접속할까요?")
③ 세션 인수      새 sessionId 기록 → 옛 기기가 스스로 물러남
④ 경기 복구 확인  resolveMyMatch() — 항상 서버에서 포인터 직접 읽기
⑤ 분기           오래 끊김 → 경기 정리(무효/몰수) + 안내 → 대기실
                 짧은 순단 → 하던 판으로 복귀
                 없음      → 대기실
```

**12.2 왜 "차단"이 아니라 "확인 후 인수"인가.** 와이파이가 팅긴 학생이 20초 만에 재접속하면
서버가 아직 끊김을 감지하기 전이라 **자기 자신의 유령이 online으로 남아 있다.**
하드 차단은 본인을 최대 60초간 자기 이름에서 쫓아낸다. 확인창 문구에는 반드시
"**다른 친구가 쓰는 이름이라면 취소**" 경고를 넣는다.

> v3 보강: 자동 닉네임이 도입되면서 이 확인창을 볼 일이 크게 줄었다.
> 이름이 기기별로 고정이라 남과 겹칠 확률이 낮고, 겹쳐도 게임 쪽 재발급(`'renick'`)으로
> 조용히 새 이름을 받아 진행할 수 있다. 기본형 템플릿의 `tryJoinRoom`이 이 경로다.

**12.3 침묵 패배 방지**: 정리할 때 결과 안내 모달을 한 번 띄운다.

**12.4 남은 모서리 (의도적 보류)**
- **유령 예약의 뒤늦은 발동**: 옛 연결의 match onDisconnect는 취소할 수 없어 수십 초 뒤 몰수될 수 있다.
- **동시 끊김 승자 뒤집힘**: onDisconnect는 트랜잭션이 아니라 일반 update. 근본 해결은
  `disconnectedAt/{me}`만 남기고 산 자가 트랜잭션으로 판정하는 구조.

## 13. 정책 스위치

| 스위치 | 짧은 판 (수십 초) | 긴 판 (수 분) | 근거 |
|---|---|---|---|
| `AWAY_AS_LOSS` | **false — 무효** | **true — 몰수패** | 10초 판에서 알림 한 번에 패배가 찍히면 승률 수업 데이터가 오염 |

| 무효 카운트 별도 필드 | `forfeits` 권장 | 불필요 | "승패에 포함되지 않습니다" 명시 |

## 14. 기본형(매칭 없는 게임) 패턴

**대기 상태를 명시한다.** `state.status`는 `'waiting' → 'playing' → 'finished'`.
방을 만들면 `waiting`이고, 학생이 모두 들어온 뒤 교사가 [게임 시작]을 눌러야 1라운드가 시작된다.
`status`가 없던 옛 방은 `'playing'`으로 간주(`roomStatus()` 폴백). **인원 제한은 두지 않는다** —
시작 후 들어온 학생도 이어서 참여한다.

**라운드 정산은 단일 원자 update로.** 점수·잔여자원·라운드 전환·잠금 해제를 한 번에 묶고,
적용 직전 **서버 상태를 새로 읽어 라운드 번호가 그대로인지** 확인한다.

**공개 연출 중 입력 잠금 + 스냅샷 채점.** 공개 시작 시 `state.revealing = 라운드`로 잠그고,
채점은 공개 시작 시점에 떠 둔 **스냅샷 배열**로 한다. 잠금은 정산 update에 `revealing: null`을
포함해 해제하고, **실패 경로와 관리자 재진입 시에도 반드시 풀어준다**(안 풀면 학생 영구 잠김).

**자동 진행은 취소 가능한 대기로.** `setTimeout` 핸들과 resolve 함수를 함께 보관해,
중지 버튼이 대기 중인 Promise를 즉시 깨우게 한다.

**강제 진행.** 미제출자를 0으로 먼저 기록한 뒤 짧은 간격으로 공개하고 마감한다.
접속이 끊긴 학생 한 명 때문에 수업이 멈추지 않게 하는 장치다.

**연출 중 재렌더 차단**(`isAnimating`), **학생은 자기 노드만 구독**(트래픽 + 정보 노출).

## 15. 관리자 대시보드 규약

### 15.1 상단 헤더는 만들지 않는다

```html
<div id="dash-header-placeholder"></div>
<script src="../../../js/dashboard-header.js"
        data-title="OOO 대시보드"
        data-export="false"              <!-- 엑셀 버튼 숨김 (기본 true) -->
        data-select-id="admin-room-select"  <!-- 기본값 roomSelect -->
        data-qr="false"></script>        <!-- QR 패널 끄기 (기본 켜짐) -->
```

자동 생성되는 id: `#btn-delete-room`, `#{selectId}`, `#btn-create-room`,
`#btn-export-excel`(옵션), `#btn-reset-pin`. 게임 페이지는 여기에 **이벤트만 연결**한다.
`$('btn-create-room')?.addEventListener(...)`처럼 **옵셔널 체이닝으로 방어적으로** 접근한다.

### 15.2 상태 판정·서식·정렬

- **`statusInfo()` 한 곳에서**: 접속중(`#198754`) / 다른화면(`#ffc107`) / 접속 끊김(`#dc3545`).
  판정은 `status` 값 **+ 하트비트 신선도(40초)** 둘 다.
- **테이블 서식**: `table table-hover text-center align-middle mb-0` + `<thead class="table-light">`.
- **정렬**: 기본은 입장순(`joinedAt`, 재접속에도 불변). 대전 게임은 접속상태 1순위 → 승수 2순위.
- **matches를 구독하지 않는다**: 대전 현황은 `players/{id}/currentOpponent`로.
- **렌더 스로틀 1초 + 5초 주기 재렌더**(DB 읽기 없음).
- **방 삭제 순서**: 구독 해제 → remove → UI 초기화 → 목록 갱신. 삭제 중 버튼 잠금.

### 15.3 방 목록은 인덱스 노드로 읽는다 ★v3 신규

```js
get(ref(db, `${GAME_KEY}_rooms`))        // ✗ 모든 방의 players·matches까지 통째로 내려받음
get(ref(db, `${GAME_KEY}_room_index`))   // ✓ 방당 필드 4개
```
30명이 한 시간 논 방 하나가 수백 KB다. 드롭다운을 열 때마다 그걸 전부 받으면
교사 기기에서 눈에 띄게 버벅인다. **방을 만들 때 `rooms`와 `room_index`에 같은 메타를 동시에 쓰고,
삭제할 때도 둘 다 지운다.** 인덱스가 없던 기존 데이터는 1회 마이그레이션한다.

```js
const idxSnap = await get(roomIndexRef());
if (!idxSnap.exists()) {
    const full = await get(ref(db, `${GAME_KEY}_rooms`));   // 최초 1회만
    /* id별 createdAt만 뽑아 update(roomIndexRef(), migrate) */
}
```
Firestore 기록형은 방 문서가 이미 가볍고 하위 컬렉션이 따로라 인덱스가 필요 없다.

### 15.4 학번은 기본으로 숨긴다 ★v3 신규

인증 모드 대시보드는 교실 TV에 그대로 투사되는 일이 많다. 학번 열은 **기본 숨김 + 토글**로 둔다.

```css
.col-studentid { display: none; }
#adminTableWrap.show-sid .col-studentid { display: table-cell; }
```
학번의 출처는 `records`의 `studentId`를 우선하고, 없으면 `students` 문서로 보완한다
(`sidByNick` 맵). 두 곳 다 없으면 `-`.

### 15.5 QR 입장 패널

`dashboard-header.js`가 같은 폴더의 `qr-modal.js`를 모듈로 자동 로드한다. **게임 페이지 코드는 0줄.**

- 방을 새로 만들거나 드롭다운에서 고르면 **자동으로** QR이 뜬다(버튼 없음).
  감시 방식은 `change` 이벤트 + **700ms 폴링** 병행 — 페이지마다 `select` 값을 바꾸는 방식이 달라
  이벤트만으로는 놓친다.
- 어떤 `<select>`를 볼지는 `window.dashboardSelectId`(= `data-select-id`)로 알려준다.
  폴백은 `#roomSelect` → `#admin-room-select`.
- 주소는 **현재 페이지 URL + `?room=코드`**. 학생이 찍으면 첫화면의 방 코드가 자동으로 채워진다.
- 제목 줄 드래그로 이동, 우하단 모서리로 크기 조절. 위치·크기는 `localStorage`에 저장.
  **끄는 동안은 CSS로 늘려 보여 주고, 손을 뗀 뒤에 실제 크기로 다시 그린다** —
  드래그 중 매 프레임 QR을 재생성하면 저사양 기기에서 멈춘다.
- `file://`에서는 QR로 접속할 수 없으므로 그 사실을 명시한다(로컬 테스트 중 가장 흔한 오해).

### 15.6 PIN 초기화

`#btn-reset-pin` → `showPinResetModal()` 한 줄이면 끝난다.

```js
$('btn-reset-pin')?.addEventListener('click', () => showPinResetModal());
```
학교 드롭다운 + 학번 직접 입력으로 `student_auth/{키}.pin = null`을 쓴다. 학생은 다음 접속 때
새 PIN을 설정한다. **"현재 방 학생 목록"에서 고르게 만들면 안 된다** — 이 기능은 애초에
방에 들어오지 못한 학생을 구제하는 용도다.

## 16. 첫화면 규약

`renderRoomEntrance(컨테이너, 옵션)` 하나로 통일한다. 페이지별 코드는 옵션 객체가 전부다.

### 16.1 화면 구성 (v3에서 바뀐 부분)

```
┌──────────────────────────┐
│      🧑‍🎓 게임 입장하기       │
│  [  방 코드 4자리 입력  ]  │   ← 입력창은 이것 하나뿐 (닉네임 입력 없음)
│  QR로 방 번호가 자동 입력…  │   ← 힌트 줄
│  ○ 게스트 모드(공용기기)    │
│  [    🎮 방 입장하기    ]   │
│  [   📖 게임방법 보기   ]   │   ← guideSlides를 넘길 때만 생김
│  [   대시보드 열기      ]   │   ← 승인 교사에게만 보임
└──────────────────────────┘
```

### 16.2 옵션

| 옵션 | 용도 |
|---|---|
| `onJoin(code, nickname, authInfo)` | **필수.** await된다. 버튼 잠금은 room-auth가 담당 |
| `onAdminSuccess` / `onAdminFailure` | 대시보드 진입 |
| `getRoomData(code)` | 방 존재 확인 + **모드 판정**. 넘기면 없는 방을 room-auth가 먼저 걸러 준다 |
| `studentsCollectionRef(code)` | Firestore 학생 컬렉션. **인증 모드·게스트 승인에 필수** |
| `guideSlides` / `guideBtnText` / `guideTitle` | 게임방법 슬라이드. 안 넘기면 버튼 자체가 없음 |
| `title` / `roomCodePlaceholder` / `joinBtnText` / `dashBtnText` | 문구 |
| `rememberLastEntry` | 지난 방 코드 자동 입력 (기본 true) |

### 16.3 규약

- **입장 정보 기억**: 성공 시점에만 `rememberEntrance(code, nickname)`. 방 코드는 **페이지 경로별**,
  닉네임은 **전역** 키. 불러올 때 입력과 같은 규칙으로 재정제(4자 대문자).
- **자동 입력 우선순위**: `?room=XXXX`(QR) **>** 지난 접속 기억. QR로 들어온 학생에게
  옛 방 코드가 남아 있으면 그날 수업이 통째로 어긋난다.
- **공용 기기 대비**: 자동 입력 시 "지난 접속 방 번호를 불러왔어요 · **지우기**" 링크 필수.
- **입력 위생**: 방 코드는 공백 제거 + 4자 + 대문자. 닉네임은 시스템 발급이지만 게임 쪽에서
  `isValidRtdbKey()`로 한 번 더 확인하고, 실패하면 재발급한다(4.4의 12자 상한 주의).
- **오류는 원인별로**: `onJoin` 전체를 try/catch로 감싸고 permission 계열이면
  "네트워크가 아니라 **보안 규칙** 문제"라고 구분해 안내한다.
- **모달 접근성**: 닫기 직전 `hide.bs.modal`에서 내부 포커스를 blur — `aria-hidden` 경고 방지.
- **모달은 큐로 직렬화**: `room-auth`의 `showCustomModal`은 내부 큐(`modalQueue`)를 써서
  한 번에 하나만 뜬다. 인증 흐름에서 모달이 연달아 필요할 때 backdrop이 겹쳐 화면이 잠기는 사고를 막는다.
  **직접 `new bootstrap.Modal(...)`을 띄우는 코드를 인증 흐름 사이에 끼워 넣지 않는다.**

## 17. 보안 규칙 설계

클라이언트 전용 구조에서 규칙은 유일한 서버측 방어선이다.

### 17.1 RTDB 대원칙

```json
{
  "rules": {
    ".read": false, ".write": false,
    "mygame_rooms":      { ".read": true, "$room": { ".write": true } },
    "mygame_room_index": { ".read": true, ".write": true }
  }
}
```

### 17.2 RTDB 함정 (전부 실제 사고)

1. **컬렉션 목록 읽기는 컬렉션 '자체'의 `.read`가 필요하다.** `$room` 하위에만 있으면
   대시보드 드롭다운이 조용히 빈다. `.read`는 아래로만 흐른다.
2. **`hasChildren` 필드명은 코드의 실제 필드명과 대조하라.** 오목의 `joinedAt`을 다른 게임 규칙에
   복사했다가(실제 필드는 `ts`) **모든 대기열 쓰기가 전멸**했다.
3. **null 가능 필드를 필수로 넣지 마라.** RTDB는 null을 저장하지 않는다.
4. **`update()`는 병합 결과로 검증된다.** 반대로 **트랜잭션은 노드 전체를 다시 쓰므로**
   필수 필드가 없는 옛 데이터에서 거부된다 — 규칙 강화 전 기존 방 정리 필수.
5. **삭제(null 쓰기)는 validate를 타지 않는다.**
6. **`matchLock`에는 TTL 상한** `until <= now + 15000`.
7. **전적 검증은 increment 호환으로**: `유지 또는 +1`만 허용.
8. **상한 있는 증가**: `<= data.val() + K`.
9. **역행 금지**: `finished → playing` 차단, `statsApplied`는 `=== true`만.
10. **키-값 일치**: `nickname`은 `newData.val() === $nick`.
11. **`root.child()` 교차 참조** 시, 트랜잭션이 노드 전체를 재작성하는 게임에선
    "기존 값 그대로면 통과" 예외를 함께 넣어야 하트비트가 안 막힌다.

### 17.3 Firestore 규칙 ★v3 신규

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // 관리자 uid를 규칙에 직접 박는다. 클라이언트의 ADMIN_EMAIL 상수는 위조 가능하다.
    function isAdmin() { return request.auth != null && request.auth.uid == '관리자_UID'; }

    match /teachers/{uid} {
      allow read: if true;                       // 학생 화면의 학교·교사 드롭다운
      allow create: if request.auth != null && request.auth.uid == uid
                    && request.resource.data.status == 'pending';
      // ★ 스스로 승인 금지: status는 관리자만 바꾼다
      allow update: if isAdmin() ||
                    (request.auth != null && request.auth.uid == uid
                     && request.resource.data.status == resource.data.status);
      allow delete: if isAdmin() || (request.auth != null && request.auth.uid == uid);
    }

    match /student_auth/{key} {
      allow read, write: if true;                // 교실용 최소 설정 — 아래 한계 참고
    }

    match /mygame_records/{roomCode} {
      allow read, write: if true;
      match /{sub=**} { allow read, write: if true; }
    }
  }
}
```

**가장 중요한 한 줄은 `teachers.status`다.** 이걸 열어 두면 아무나 가입해서 스스로를 승인하고
전체 방을 보게 된다.

### 17.4 남는 한계를 알고 써라

- **PIN은 평문이고 읽을 수 있다.** 클라이언트가 직접 비교하는 구조라 읽기를 막을 수 없고,
  Firestore 규칙은 문서 단위라 필드 하나만 숨기지도 못한다. 현재 PIN은
  "같은 반 친구가 장난으로 내 학번을 쓰는 것"을 막는 수준이며, **비밀번호가 아니다.**
  학생 안내 문구에도 "다른 비밀번호와 다른 숫자를 쓰세요"를 넣는다.
  제대로 막으려면 Anonymous Auth + Cloud Functions(서버 검증)로 올려야 한다.
- 인증이 없으면 방 삭제, +1 반복 파밍, 남의 노드 삭제는 못 막는다.
- 콘솔을 여는 학생이 실제로 관찰되면 그때 **Anonymous Auth**를 붙여
  "자기 uid 노드만 수정 / 방 삭제는 교사 uid만"으로 올린다. `sessionId`가 그 수제 전신이라 이식이 자연스럽다.

## 18. 함정 대사전

표의 모든 행이 이 프로젝트에서 실제로 발생했다.

### 18.1 인증·신원 ★v3 신규

| 함정 | 증상 | 해법 |
|---|---|---|
| `window.isAdmin`을 페이지 로드 직후 읽음 | 방 목록이 항상 비거나 남의 방이 보임 | `teacherAuthChanged` 이벤트에서 재로딩 (2.2) |
| 방 소유권 필드 없이 목록 표시 | 다른 학교 교사의 방이 드롭다운에 섞임 | `createdBy` + `creatorEmail` 둘 다 확인 (3.2) |
| 소유권 확인에서 옛 방까지 차단 | 필드 없는 기존 방을 아무도 못 지움 | `rData.createdBy &&` 조건 선행 |
| `teachers.status`를 본인이 수정 가능 | 자가 승인 → 전체 방 열람 | 규칙에서 status 변경은 관리자만 (17.3) |
| 교사 정보 수정 후 캐시 미갱신 | 학생 화면에 옛 학교명이 계속 뜸 | `window.clearTeacherCache()` |
| 게스트 경로가 `localStorage`를 건드림 | **앞 학생 계정을 덮어씀** | 게스트는 `sessionStorage`만 (4.6) |
| PIN 불일치를 첫화면으로 되돌림 | 학생이 원인을 모른 채 반복 실패 | 모달 안에서 `continue`로 재입력 |
| 클라이언트가 기존 PIN을 덮어씀 | 남의 학번을 PIN째로 탈취 | `pin === null`일 때만 기록 (4.5) |
| `isAccountOnline`을 status로만 판정 | 조용히 끊긴 계정이 영구 잠김 | presence + `lastActive` 90초 신선도 |
| Firestore **배열 안에 `serverTimestamp()`** | 쓰기 실패 / 센티널이 그대로 저장 | `devices`는 `Date.now()` 밀리초 |
| 닉네임 정규식 상한 10자 | 충돌 폴백(11~12자)을 만난 학생만 입장 거부 | 상한 12자 (4.4) |
| 인증 모드에서 게임이 닉네임을 갈아엎음 | 기록이 두 갈래로 쪼개짐 | `mode==='auth'`면 이름 변경 금지 (4.7) |
| `nicknameFixed` 무시하고 매번 중복 검사 | 입장할 때마다 전 방 순회 → 수십 회 읽기 | 플래그가 false일 때만 검사 |
| `studentsCollectionRef` 없이 인증 모드 방 생성 | 게스트 대기 모달이 안 닫힘 | RTDB 게임은 `roomMode:'quick'` 고정 (4.6) |
| 인증 흐름 중간에 직접 bootstrap 모달 호출 | backdrop이 겹쳐 화면 잠김 | `showCustomModal` 큐 사용 (16.3) |

### 18.2 RTDB · SDK

| 함정 | 증상 | 해법 |
|---|---|---|
| 트랜잭션 첫 콜백의 `null` | 기존 전적이 통째로 덮임 | 카운터는 `increment()` |
| 트랜잭션 안 `serverTimestamp()` | 센티널이 저장되어 시간 계산 붕괴 | `serverNow()` 값 |
| 트랜잭션 중단법 혼동 | 의도치 않은 쓰기 | 중단은 `return;`, 판정은 `res.committed` |
| **`set()`에 merge 옵션 없음** (Firestore 혼동) | 노드 통째 덮임 → 닉네임·점수 소멸 | 부분 갱신은 `update()` |
| **Firestore API 혼입**(`updateDoc`, `doc`) | ReferenceError — 기능 전체 무동작 | RTDB는 `update(ref(...))`만 |
| **빈 객체는 저장 안 됨** | `p.rounds[r]`에서 TypeError → 렌더 전멸 | 모든 접근에 `(p.rounds \|\| {})` |
| **`numChildren()` vs `size`** | v9엔 numChildren 없음. 첫 사람만 되고 둘째부터 실패 | `countChildren()` 안전판 |
| 방 목록을 `rooms` 전체 읽기로 | 드롭다운 열 때마다 수백 KB | `room_index` 노드 (15.3) |
| 다중 경로 update 분할 | 반쪽 매칭·부분 정산 잔류 | 단일 `update()` |
| onDisconnect는 일반 update | 동시 끊김 시 승자 뒤집힘 | 인지, 근본은 `disconnectedAt` 구조 |

## 19. 새 게임 체크리스트

**0. 계열 선택** — 1:1 대전이면 `realtime-matching`, 각자 진행이면 `realtime-basic`,
개인 스테이지 학습이면 `stage-basic`을 복사.

**1. 식별자** — `GAME_KEY` 변경, `firebase-config.js`에 이 게임용 DB 인스턴스를 export하고 import 교체.
게임마다 DB 인스턴스를 분리하면 규칙·데이터·트래픽이 서로 격리된다.

**2. `[TODO]` 채우기** — `Ctrl+F "[TODO"`.

**3. 인증·소유권 연결 4줄** (빠뜨리면 다른 교사의 방이 섞인다)
   - [ ] 방 생성 시 `createdBy` / `creatorEmail` / `creatorName` 기록
   - [ ] 방 생성 시 `roomMode` 기록 (RTDB 게임은 `'quick'` 고정)
   - [ ] 목록에서 `!window.isAdmin`이면 내 방만 필터, 0건이면 안내 문구
   - [ ] `window.addEventListener('teacherAuthChanged', () => loadRooms())`

**4. 닉네임 규약 3줄**
   - [ ] `onJoin(code, nickname, authInfo)` — 세 번째 인자를 받는다
   - [ ] RTDB 키로 못 쓰는 값이면 `generateRandomNickname()` + `saveGameNickname()`
   - [ ] `authInfo.mode === 'auth'`면 이름을 바꾸지 않는다
   - [ ] `NICKNAME_RE` 상한 **12자**

**5. 정책 스위치** — 13장 표에서 판 길이에 맞게.

**6. 보안 규칙** — RTDB(17.1~17.2) + Firestore(17.3). 게임별 필드를 추가했다면 함정 목록과 대조.

**7. 검증 시나리오 (배포 전 최소 세트)**
   - [ ] 로그아웃 상태: 대시보드 버튼이 안 보임 / 로그인 → 즉시 보임 (`teacherAuthChanged`)
   - [ ] 교사 A가 만든 방이 교사 B의 드롭다운에 **안 보임**, 관리자에겐 보임
   - [ ] 방 생성 → QR 자동 표시 → 다른 기기로 스캔 → 방 코드 자동 입력 → 입장
   - [ ] 같은 기기로 두 번 입장 → **닉네임이 같은지** 확인 (게임별 고정)
   - [ ] 다른 게임 페이지에서 입장 → **닉네임이 다른지** 확인
   - [ ] (인증 모드) 최초 등록 → 재입장 시 확인 모달 → [맞아요] 통과
   - [ ] (인증 모드) 다른 학번 + 틀린 PIN → 차단, 모달에서 재입력 가능
   - [ ] (인증 모드) 게스트 스위치 → 교사 승인 배너 → 승인 → 입장 → 종료 버튼으로 복귀
   - [ ] PIN 초기화 → 학생 재접속 시 새 PIN 설정 모달
   - [ ] 매칭형: 2명 매칭 → 한쪽 새로고침 → 몇 초 내 종료 안내 + 재접속자 결과 안내
   - [ ] 매칭형: 대기 2명이 직전 상대끼리 → 즉시 재매칭 (교착 없음)
   - [ ] 교사: 강퇴 → 상대 정상 정리 → 방 삭제 → 학생 안내 후 첫화면
   - [ ] 콘솔(F12)에 `permission_denied` 0건 — 한 건이라도 있으면 17.2의 1·2·3번부터 의심
   - [ ] 모바일 세로 화면에서 게임 화면이 한 눈에 들어오는지 (21.5)

**8. 운영 습관** — 수업 후 방 삭제(다음 반은 새 방), 같은 방 재사용 금지.

### 20.4 스크롤 스냅 룰렛 위젯 ★v3 신규

좌표·계수처럼 **정수 하나를 고르는 입력**은 `<input type="number">`보다 룰렛이 낫다.
모바일 키보드가 안 뜨고, 범위가 눈에 보이고, 오타가 불가능하다. 대신 함정이 촘촘하다.

```
[구조]  .roulette-wrapper (overflow-x:scroll, scroll-snap-type:x mandatory)
          └ .roulette-inner (inline-flex)
               ├ 패딩 아이템 (좌)
               ├ .coord-item × N   (scroll-snap-align:center)
               └ 패딩 아이템 (우)
```

1. **항목 폭 = 실측 폭 ÷ 7.** "가운데 1칸 + 양옆 3칸"이 항상 보이게 고정한다.
   `ResizeObserver`로 폭이 바뀔 때마다 다시 만든다.
2. **좌우 패딩 = (3 + 여유 1)칸.** 여유 1칸이 없으면 **끝값(±최댓값)만** 스크롤 경계 클램프에
   의존해 중앙 정렬이 1~2px 어긋난다. 끝값도 중간값과 똑같은 스냅 메커니즘을 타게 한다.
3. **값 표시 배지의 폭을 완전히 고정한다**(`width: 3.4rem`, `min-width` 아님).
   `-20`처럼 자릿수가 늘면 배지가 커지고 → 룰렛 폭이 줄고 → `ResizeObserver`가 재생성하고 →
   값이 바뀌고 → 다시 배지 폭이 바뀌는 **진동 루프**가 생긴다. 자릿수 경계에서만 재현돼서
   원인 찾기가 가장 오래 걸렸다.
4. **스크롤·드래그 중에는 절대 재생성하지 않는다.** 스크롤 유휴 200ms 뒤로 미룬다(`rebuildPending`).
5. **`clientWidth === 0`이면 만들지 않는다.** `display:none` 상태(다른 섹션)에서 실측하면 전부 0이다.
   화면 전환 직후 `requestAnimationFrame(build)`로 다시 부른다.
6. **선택 표시는 고정된 강조창(`::after` 테두리)이 아니라 숫자에 붙는 알약**으로.
   끝값 근처에서 옆이 빈 여백일 때 테두리가 "숫자 옆의 이상한 파란 선"처럼 보인다.
7. **`overscroll-behavior-x: none` + `-webkit-tap-highlight-color: transparent`.**
   `contain`은 부모 전파만 막고 자체 글로우는 남는다.
8. **값 지정은 한 프레임 안에서 동기적으로**(배지·수식·강조·스크롤 위치 전부).
   스크롤만 `requestAnimationFrame`으로 미루면 기본 위치(첫 항목)가 한 프레임 보였다가 튄다.
9. **입력 범위 = 출제 범위.** 슬라이더가 ±24인데 출제 최대가 ±20이면 죽은 구간이,
   반대면 못 맞히는 문제가 생긴다.

## 21. 스테이지형 학습게임 패턴 (기록형)

개인이 개념 스테이지를 깨고 교사가 성취를 평가하는 계열. RTDB 대신 **Firestore**를 쓰고,
세션·하트비트·onDisconnect·매칭이 전부 없다. 학생 기기는 저장 두 시점 외에 DB를 건드리지 않는다.

### 21.1 스테이지 구조 규약

- **개념 스테이지 N개 + 마지막 혼합 스테이지 1개**(무한 모드). 스테이지당 **3문제**:
  1·2번은 현재 개념의 새 문제, **3번은 이전 개념 복습**(무작위 1개).
  1스테이지는 복습할 게 없으니 3번도 자기 개념, 요소 수만 복습 규칙을 따른다.
- **문제별 요소 수**: 1번 4개 → 2번 3개 → 3번 2~3개 무작위.
- **혼합 스테이지의 첫 문제를 깨는 순간이 상수준 판정 시점**이다. `saveClearRecord`를 즉시 남기고
  무한 챌린지를 계속한다. "플레이 종료" 버튼의 판정, 대시보드의 성취 '상' 판정도 **같은 기준**으로.
- **혼합 스테이지 시도 제한 = 필요 최소 횟수 + 1.** 시도가 남아있는 동안은 실패해도 목숨 유지.
  **시도 소진 + 목표 잔존이면 목숨 1 차감 → 새 배치 + 시도 리필.**
  소진 상태(0회)로 화면에 머무는 경로를 아예 없애는 게 핵심이다.

### 21.2 출제 정합성

- **표시 공간을 줄이면 출제 풀을 전수 재검증하라.** 격자를 ±10→±8로 줄이자 `y=5x`의 격자점이
  2개뿐이 되어 "1번 문제 요소 4개" 규칙이 조용히 깨졌다.
  모든 출제 파라미터에 대해 *배치 가능한 자리 수 ≥ 문제당 요소 수*를 확인하고 모자라는 건 뺀다.
- **입력 범위 = 출제 범위** (20.4의 9번).

### 21.3 저장 규약 — 딱 두 시점

- Firestore 쓰기는 **gameOver(모든 판)와 saveClearRecord(상수준 달성)** 뿐이다.
  진행 중 실시간 저장(`updateLiveStatus`)은 **비활성화**한다 — 무료 사용량 보호.
  대가로 **중간 이탈 = 그 판 소실**임을 알고 설계한다.
- 보완은 **localStorage 스냅샷 이어하기**(DB 쓰기 0회). 목표 배치는 저장하지 않는다 —
  *같은 지점의 새 문제*면 충분하다. `beforeunload`의 DB 저장은 모바일에서 보장되지 않는다.
- **인증 모드면 `school`/`studentId`를 records와 students에 함께 남긴다.**
  대시보드 학번 열과 엑셀 내보내기가 이 값을 쓴다.
- **대시보드 통계는 `records`만으로 재구성**한다 — 요약 필드가 깨져도 원본이 남는다.

### 21.4 대시보드

- **개념별 평균 정답률 막대**, **성취 3단계**(상 = 상수준 기록 보유, 중 = 중반 개념 도달, 하),
  **평균 풀이 속도 분포**는 20초 구간 + 마지막은 **"60초 이상" 열린 구간**으로
  (구간을 닫으면 최하위권이 표에서 사라진다).
- **게스트 승인 배너**를 표 위에 둔다. 대기자가 0명이면 영역 자체를 비운다.
  승인은 `students/{닉}.status = 'online'`과 `student_auth/{키}.presence = 'online'` **둘 다** 쓴다.
- 학생 행 클릭 → 판별 이력 + 개념별 누적 모달, 엑셀 내보내기(개념 열은 `CONCEPTS`에서 동적 생성).
- **명예의 전당은 방 통합**이므로 닉네임이 겹치면 기록이 섞인다.
  `quick` 모드 + `nicknameFixed === false`일 때만 전 방 순회 중복 검사를 돌린다(4.7).

### 21.5 모바일 규약

- **767px 미만 컴팩트 미디어쿼리**: 상단 여백·헤더 패딩·컨트롤 간격·수식 크기를 일괄 축소
  (좀비헌터 기준 세로 약 180px 절약). **컨트롤은 균등 분할 행**
  (`.control-row > * { flex: 1 1 0; min-width: 0 }`) — 선택 버튼과 상태 표시를 한 행에.
- **캔버스는 범위를 줄이고 셀을 키워라**: ±10 격자·28px 셀 → ±8 격자·34px 셀 ≈ 21% 확대.
  축 숫자는 bold 20px 이상.
- **캔버스 내부에는 CSS 미디어쿼리가 통하지 않는다.** 다크모드 색 분기는
  `matchMedia('(prefers-color-scheme: dark)')`로 하고 change 리스너에서 다시 그린다.
- **곡선·도형은 격자 사각형으로 클리핑**한 뒤 그린다. 안 그러면 값이 큰 구간이 격자 밖으로 삐져나가고,
  반대로 점근선 근처를 건너뛰면 곡선이 중간에 끊겨 보인다(`|x| < 0.2` 구간을 통째로 건너뛰던 버그).
- **페이지 단독 라이트모드 강제는 실패했다**: `color-scheme: light only`는 공통 CSS의
  `prefers-color-scheme` 판정을 바꾸지 못한다. 테마 충돌은 **공통 CSS에서 원인을 찾아** 고친다.

## 마치며

v2의 한 문장은 그대로다.
**"모두가 동시에 실행해도 되는 코드 + 한 명만 통과하는 트랜잭션 관문 + 한 번에 끝내는 원자적 쓰기",
그리고 "서버에 남긴 예약은 반드시 해제 규율과 함께, 규칙은 코드의 실제 필드와 대조하며."**

v3가 더한 문장은 이것이다.
**"학생에게 자기 신원을 입력하게 하지 마라. 이름은 발급하고, 학번은 검증하고, 저장소는 분리하고,
교사의 방은 교사의 것으로 두어라."**

나머지는 전부 이 문장들의 각주다.
