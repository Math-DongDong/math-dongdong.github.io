# 실시간 교실 게임 설계 가이드 v2

> Firebase RTDB + 순수 JS(서버 없음)로 만든 교실용 실시간 게임 3종
> (**가위바위보 · 좌표평면 오목 · 블로토**)을 실제 수업에서 운영하며
> 사고를 겪고 고친 결과를 정리한 최종 아키텍처 문서입니다.
>
> v1과의 차이: v1은 두 구현을 비교·분석했습니다. v2는 그 이후 확립된
> **통일 설계, 세션 관리, 재접속, 보안 규칙, 매칭 없는 게임 패턴**까지 포함해
> "이대로 만들면 된다"는 기준서로 다시 썼습니다.

- **대상 환경**: Firebase Realtime Database + 클라이언트 전용 (보안 규칙으로만 방어)
- **사용 상황**: 교실 20~35명 동시 접속, 크롬북·태블릿 혼재, 학교 와이파이
- **함께 쓰는 파일**:

| 파일 | 역할 |
|---|---|
| `realtime-matching.html` | 1:1 자동 매칭 게임 뼈대 (이 문서 3~10장 구현체) |
| `realtime-basic.html` | 매칭 없는 게임 뼈대 (이 문서 11장 구현체) |
| `stage-ranking.html` | 스테이지형 학습게임 뼈대 — 기록형·Firestore (이 문서 18장 구현체) |
| `js/room-auth.js` | 입장 카드·모달·게임방법 슬라이드·입장정보 기억 공통 모듈 |
| `js/dashboard-header.js` | 대시보드 상단(방 선택·생성·삭제) 공통 모듈 |
| 이 문서 | 위 코드가 **왜** 그렇게 생겼는지 + 함정 대사전 |

**설계 원칙 3줄 요약** (v1과 동일 — 여전히 전부다)

1. 여러 클라이언트가 동시에 실행해도 되는 코드로 짜되, **딱 한 명만 성공하는 관문**(트랜잭션)을 통과시킨다.
2. 상태 변경은 **여러 경로를 한 번의 `update()`로** 묶어 원자적으로 처리한다.
3. 시간 판정은 `Date.now()`가 아니라 **서버 보정 시각**으로 한다.

## 1. 두 가지 게임 계열

새 게임을 기획하면 먼저 계열부터 정한다. 이후의 모든 결정이 여기서 갈린다.

| | **기본형** (`template-basic`) | **매칭형** (`template-matching`) |
|---|---|---|
| 구조 | 각자(모둠) 진행, 교사가 전체 관찰 | 대기실 → 1:1 자동 대전 → 복귀 |
| 예시 | 블로토 | 가위바위보, 오목 |
| 필요한 층 | 세션 + 하트비트 + 대시보드 | + 대기열 + 매칭 + 경기 수명주기 |
| 난이도 | 경합 지점이 적음 | 경합 지점이 설계의 전부 |

두 계열의 **공통 계층**(세션·하트비트·onDisconnect·대시보드·첫화면·보안 규칙 골격)은 완전히 동일하다. 매칭형은 그 위에 5~9장이 얹힌 것이다.

```
[공통]  입장 검증 → 세션 발급 → 하트비트 → (게임) → 대시보드 관찰
[매칭형 추가]  대기실 등록 → 매칭 6단계 → 포인터 진입 → 경기 → 정산 → 복귀
```

표의 두 계열은 모두 **실시간(RTDB)**이다. 실시간 층이 아예 필요 없는 세 번째 계열 — 개인이 스테이지를 깨고 교사가 성취를 평가하는 **기록형(Firestore)** — 은 **18장 스테이지형 학습게임 패턴**에 따로 정리했다. 세션·하트비트·onDisconnect가 전부 불필요해 이 문서의 3~10장을 건너뛴다.

## 2. 데이터 모델 (최종형)

### 2.1 매칭형

```
{GAME_KEY}_rooms/{ROOM_CODE}
├─ createdAt        : number
├─ matchLock        : { by, until }            // 매칭 잠금 (TTL 3초, 규칙 상한 15초)
├─ players/{닉네임}
│   ├─ nickname     : string  (= 키와 동일)
│   ├─ wins, losses : number
│   ├─ status       : 'online' | 'away' | 'offline'
│   ├─ lastHeartbeat: number
│   ├─ joinedAt     : number                   // 최초 입장 1회만, 재접속에도 불변
│   ├─ sessionId    : string     ★ 중복 접속 감지 (마지막 기기가 이김)
│   ├─ currentMatchId  : matchId | null  ★ 경기 진입 포인터
│   ├─ currentOpponent : 닉네임 | null    ★ 대시보드용 (matches 비구독의 열쇠)
│   └─ lastOpponent    : 닉네임 | null    ★ 재대결 회피 (새로고침에도 유지)
├─ waiting/{닉네임}                             ★★ 매칭 판정의 모든 정보가 이 안에
│   ├─ ts       : number   // 대기 순서. 한 번 쓰고 절대 안 바꿈
│   ├─ alive    : number   // 생존 신호. 하트비트 틱마다 갱신
│   ├─ visible  : boolean  // 화면을 실제로 보는가. visibilitychange 즉시 반영
│   └─ last     : 닉네임 | null   // 직전 상대 (양방향 회피 판단용)
└─ matches/{matchId}
    ├─ p1, p2        : 닉네임
    ├─ status        : 'playing' | 'finished'
    ├─ winner        : 닉네임 | null           // null = 무효(승패 미기록)
    ├─ endReason     : 17장 사전 참고
    ├─ createdAt, lastMoveTime : number        // 타이머 기준 = lastMoveTime(서버 기록)
    ├─ statsApplied  : true    ★ 전적 반영 도장 (1회만)
    └─ (게임별) moves, currentTurn, choices, winLine ...
```

### 2.2 v1에서 달라진 핵심: `waiting` 노드의 자급자족

v1 시점에는 활성 판정을 위해 오목이 `players` 컬렉션 전체를 구독했다. 30명이 10초마다 쓰는 하트비트를 대기실의 전원이 실시간 수신하는, **교실에서 가장 비싼 구독**이었다. 최종형은 판정에 필요한 정보(`alive`·`visible`·`last`)를 `waiting` 항목 안에 넣어 이 구독을 **삭제**했다.

얻은 것:
- 유령 대기자(탭 켠 채 와이파이 끊김)가 25초 뒤 자동으로 후보에서 탈락 → **대기실 잠김 교착 소멸**
- 대기자만 쓰고 대기자만 받으므로 **매칭될수록 트래픽이 0을 향해 감소**
- 리더 선출·상대 선택이 **스냅샷 하나** 안에서 끝남 → 서로 다른 시점의 두 스냅샷을 조인하던 어긋남과 잠금 경합 소멸

### 2.3 설계 포인트 (필드별 존재 이유)

| 필드 | 왜 필요한가 |
|---|---|
| `currentMatchId` 포인터 | matches 전체 구독을 피하는 유일한 길. 덤으로 재접속 복구가 공짜 |
| `waiting.visible` | 다른 앱을 보는 학생과 매칭되면 상대가 허공에 기다림. 즉시성은 하트비트(≤10초 지연)보다 우월 |
| `waiting.alive` | visible만으로는 유령을 못 잡음(끊겨도 true로 남음). 25초 신선도로 보완 |
| `waiting.last` + `players.lastOpponent` | 양방향 재대결 회피. DB 저장이라 새로고침에도 유지 |
| `sessionId` | "마지막 접속 기기가 이김". 이중 집계·선택 덮어쓰기 원천 차단 |
| `statsApplied` | 리스너 중복 발화·새로고침·강퇴·onDisconnect 등 **누가 몇 번 불러도** 전적 1회 반영 |
| `currentOpponent` | 교사 화면이 matches를 구독할 필요를 없앰 |
| `joinedAt` (players) | 대시보드 입장순 정렬. 재접속 시 갱신 금지가 핵심 |

> **일반화**: 게임이 바뀌어도 `players / waiting / matches / matchLock` 네 갈래와
> 포인터·도장·sessionId 세 장치는 그대로다. 바뀌는 건 `matches/{id}` 내부뿐.

## 3. 기반 장치 — 서버 시간 · 하트비트 · onDisconnect

### 3.1 서버 시간 동기화

학생 태블릿의 시계는 몇 분씩 틀어져 있다. 모든 시간 비교는 서버 보정 시각으로 한다.

```js
let serverOffset = 0;
onValue(ref(db, '.info/serverTimeOffset'), s => serverOffset = s.val() || 0);
const serverNow = () => Date.now() + serverOffset;
```

규칙: DB **기록**은 가능하면 `serverTimestamp()` 센티널, 단 **트랜잭션 안에서는 센티널이 해석되지 않으므로** `serverNow()` 값을 직접 쓴다.

### 3.2 하트비트 — 반드시 트랜잭션으로

```js
const HEARTBEAT_MS = 10000;

async function updateHeartbeat() {
    if (!currentRoomCode || !currentNickname || isKicked || isTeacher) return;
    await runTransaction(playerRef(room, me), (cur) => {
        if (cur === null) return;              // ★ 삭제(강퇴)됨 → 부활 금지
        cur.lastHeartbeat = serverNow();
        cur.status = document.hidden ? 'away' : 'online';
        return cur;
    });
    // 매칭형: 대기실이면 대기열 생존 신호도 함께 갱신
    if (대기실화면) update(waitingRef(room, me), { alive: serverTimestamp() });
}
```

단순 `update()`를 쓰면 안 되는 이유 두 가지가 실제로 터졌다: ① 강퇴된 학생의 낡은 클라이언트가 3초 뒤 유령 노드를 되살림, ② 교사가 방을 삭제한 직후 학생 하트비트가 **삭제된 방을 부분 부활**시킴. `cur === null → return`(중단)이 둘 다 막는다.

`visibilitychange` 핸들러는 4가지를 한다: 상태 즉시 반영, 대기실이면 `visible+alive` 즉시 갱신, 경기 중 이탈이면 유예 타이머 시작, 복귀하면 해제.

### 3.3 onDisconnect 3종과 "해제 규율"

연결이 끊기면 서버가 대신 실행하는 예약. 브라우저 강제 종료·와이파이 단절처럼 "인사 없이 사라지는" 경우의 유일한 방어선이다.

| 대상 | 예약 내용 | 막는 사고 |
|---|---|---|
| `players/{me}` | `{status:'offline', currentMatchId:null}` | 유령 접속자 잔류 |
| `waiting/{me}` | `remove()` | 사라진 학생이 1순위로 남아 **대기실 전체 잠김** |
| `matches/{id}` | `{status:'finished', winner, endReason:'offline'}` | 상대가 빈 화면을 무한 대기 |

**예약보다 중요한 것이 해제다.** 이 대화에서 가장 반복적으로 터진 사고 계열:

- 경기가 정상 종료됐는데 match 예약을 `cancel()` 안 함 → 나중에 브라우저를 닫는 순간 **끝난 경기가 몰수로 덮어써짐**. → 경기가 끝나는 **모든** 경로(정상·무효·취소·삭제·복귀·강퇴·세션정리)에서 `disarmMatchDisconnect()`.
- 중복 접속으로 물러나는 기기가 예약을 안 지운 채 `location.reload()` → reload는 연결 종료이므로 예약이 발동해 **새 기기의 상태를 offline으로 덮고, 진행 중 경기를 몰수 처리**. → `cleanupAll()` 첫 줄에서 예약 3종 전부 취소.
- 물러나는 기기가 `waiting/{me}`를 **직접 삭제**하면 그건 새 기기의 항목이다. → 정리 시에는 구독·예약만 해제하고 항목은 남긴다(`stopWaiting(false)` / `cleanupWaiting(false)`).

한계 하나는 설계상 남는다: **다른 연결의 예약은 취소할 수 없다.** 세션을 이어받은 뒤에도 옛 연결의 match 예약은 서버가 끊김을 감지하는 순간 발동할 수 있다(9.4 참고).

## 4. 세션 관리 — sessionId 인수와 정리 규율

목표: 같은 닉네임의 기기가 둘이 되는 순간을 **"마지막 기기가 이김"**으로 정리한다.

```
입장 시  localSessionId = Date.now() + 랜덤4자
        update(players/{me}, { sessionId: localSessionId, ... })

상시    unsubMe = onValue(players/{me}, snap => {
            if (!snap.exists())           → 강퇴/삭제 → cleanupAll() → 안내 → reload
            if (snap.sessionId ≠ 내 것)  → 인수당함 → cleanupAll() → 안내 → reload
        })
```

핵심 규율:

- **`isKicked` 플래그**: 물러난 세션의 하트비트·매칭·쓰기를 전부 가드. 없으면 유령 쓰기가 계속된다.
- **`sessionEnded` 플래그**: 방 삭제 감지(unsubRoom)와 세션 감지(unsubMe)가 동시에 울려 안내 모달이 두 번 뜨는 것 방지.
- **`cleanupAll()`은 reload 직전에 반드시**: 3.3의 예약 해제 규율이 여기서 실행된다.
- 교사(isTeacher)는 이 감시에서 제외 — 교사는 player 노드가 없다.

중복 접속 **차단이 아니라 인수**인 이유는 9장(자기 유령 문제)에서.

## 5. 매칭 6단계 (최종형)

두 매칭형 게임이 최종적으로 수렴한 형태. 이 블록은 게임 내용과 완전히 무관하며 그대로 재사용한다.

```
① 활성 대기자 필터  : visible === true && (now − alive) < 25초
② 리더 선출        : ts가 가장 이른 활성 대기자 == 나 (아니면 즉시 return)
③ 상대 선택        : 직전 상대 양방향 회피 → 대안 없으면 즉시 폴백 → 무작위(또는 선입)
④ matchLock 선점   : 트랜잭션, TTL 3초 (실패는 정상 — 조용히 return)
⑤ 재확인          : 서버에서 waiting을 새로 읽어 양쪽 잔류 확인
⑥ 원자적 성사      : 단일 update()로 경기 생성 + 포인터 + lastOpponent
                     + 대기열 제거 + 잠금 해제를 전부 한 번에
```

### 단계별 근거 (실제 사고 기준)

**① 활성 필터 — visible과 alive는 보완 관계다.** visible만 쓰면(초기 가위바위보) 탭이 켜진 채 와이파이가 끊긴 학생의 visible이 true로 남아 **대기열 맨 앞을 영구 점거**한다. onDisconnect의 waiting 삭제는 서버가 죽은 연결을 감지할 때까지 수십 초 걸리고, 그동안 교실 전체가 "매칭이 안 돼요"가 된다. alive 신선도(하트비트×2.5 = 25초)가 이 유령을 자동 탈락시킨다. 반대로 alive만 쓰면 앱을 전환한 학생이 최대 10초간 후보로 남는다 — visible이 그 즉시성을 준다. 15초 신선도는 학교 와이파이에서 여유가 5초뿐이라 오탐이 잦았다(→25초).

**② 리더 선출만으로는 부족하다.** 서버 시간 보정에도 오차가 있고, 두 클라이언트가 서로 다른 스냅샷을 보는 순간 둘 다 자기가 리더라고 믿을 수 있다. 그래서 ④가 최종 방어선이다.

**③ 폴백은 필수다.** 대기자가 2명뿐이고 서로 직전 상대이면, 폴백 없이는 영원히 매칭되지 않는다. "대안이 있을 때만 회피"가 정답이며, 시간 기반 해제(예: 20초 후 허용)보다 단순하고 교착이 없다. 양방향 확인(`후보 ≠ 내 직전상대 && 나 ≠ 후보의 last`)은 한쪽만 기억하는 비대칭을 막는다.

**④ 잠금의 3원칙.** 중단은 `return;`(undefined)이고 `res.committed`가 승패다. **TTL이 없으면 잠금 보유자가 죽는 순간 방 전체가 영구 동결**된다(코드 3초, 보안 규칙 상한 15초로 이중 방어). 실패는 에러가 아니라 정상 — 다음 틱에 재시도.

**⑤ 재확인은 캐시가 아니라 서버 `get()`으로.** 잠금을 얻는 수백 ms 사이에 상대가 나갔을 수 있다.

**⑥ 쪼개면 안 되는 이유.** 여러 `set()`으로 나누면 중간에 끊겼을 때 "경기는 생겼는데 대기열에 남은 학생", "한쪽만 포인터가 걸린 반쪽 매칭"이 생긴다. RTDB 다중 경로 update는 전부 성공하거나 전부 실패한다. `matchLock: null`을 같은 update에 넣어 성사와 동시에 해제한다.

### 실행 골격

```js
async function attemptMatch() {
    if (currentMatchId || isMatching || isKicked) return;   // 재진입 가드
    isMatching = true;
    let lockHeld = false;
    try {
        /* ①~⑥ */
    } finally {
        isMatching = false;
        if (lockHeld) await set(matchLockRef(room), null).catch(() => {});  // 예외 시 잠금 반납
    }
}
```

**트리거는 이벤트 + 저빈도 폴링 병행**: waiting `onValue` + `setInterval(attemptMatch, 1500)`. 이벤트만 쓰면 마지막 스냅샷 이후 쓰기가 없을 때 매칭이 멈출 수 있고, 폴링은 로컬 캐시만 읽으므로 비용이 거의 없다.

## 6. 경기 진입 3중 안전망

매칭을 성사시킨 리더는 matchId를 안다. **상대가 그것을 아는 경로**가 이 장이다. "A는 게임중인데 B는 대기실" 사고(실제 발생)의 재발 방지 구조.

```
[안전망 1] 포인터 전용 구독 (주 방어선)
    onValue(players/{me}/currentMatchId) → 값이 오면 경기 1건만 get → 검증 → enterGame
    · isMatching 플래그와도, 로컬 캐시와도 무관 — 서버가 밀어줌
    · 검증 3종: status==='playing' / 내가 참가자 / currentMatchId 미중복

[안전망 2] 매칭 루프 앞머리의 서버 확인
    attemptMatch() 첫 줄에서 resolveMyMatch() — 포인터를 항상 서버 get으로 읽음
    · "로컬 캐시가 낡아 매칭 성사를 영영 모르는" 사고의 직접 원인 제거

[안전망 3] 1.5초 폴링
    스냅샷 유실·구독 순단까지 회복
```

세 경로가 전부 **`enterGame(mid, m)` 하나로 수렴**하고, 그 첫 줄 `if (currentMatchId) return;`이 중복 진입을 막는다. enterGame은 대기실 정리 → 상태 세팅 → `myLastOpponent` 갱신 → match onDisconnect 무장 → 구독 시작을 담당한다.

`resolveMyMatch()`는 재접속 복구에도 그대로 쓰인다: 포인터가 가리키는 경기가 없거나 끝났으면 **정산 확인 후 포인터를 정리**하고 null을 반환한다. 그리고 대기실에 **들어갈 때마다 포인터를 null로 초기화**해야 끝난 옛 경기로 되돌아가지 않는다.

## 7. 경기 종료·정산 — 멱등성

버그가 가장 많이 나오는 지점. **종료 확정**과 **전적 반영**을 분리하고, 각각 트랜잭션으로 1회만 성공하게 한다.

### 7.1 종료 확정 — `finishMatchAtomic`

```js
async function finishMatchAtomic(matchId, winnerId, reason) {
    const res = await runTransaction(matchRef(room, matchId), (cur) => {
        if (!cur || cur.status !== 'playing') return;   // 이미 끝남 → 중단
        cur.status = 'finished';
        cur.winner = winnerId || null;   // null = 무효 (승패 미기록)
        cur.endReason = reason;
        return cur;
    });
    return res.committed;
}
```

호출 주체가 이렇게 많아서 원자성이 필수다: 승리 판정 / 본인 이탈 / 상대 감시 / 정체 감지 / 수동 취소 / 강퇴 / onDisconnect(서버) / 재접속 정리. 누가 몇 명이 동시에 불러도 딱 1명만 committed.

### 7.2 전적 반영 — `settleMatch` (공용 도장)

```js
async function settleMatch(matchId, data) {
    if (!data || data.status !== 'finished' || data.statsApplied) return;
    // 도장 선점 — 먼저 찍은 1명만 통과
    const res = await runTransaction(
        ref(db, `.../matches/${matchId}/statsApplied`),
        (cur) => (cur === true ? undefined : true));
    if (!res.committed) return;

    const winnerValid = data.winner && (data.winner === data.p1 || data.winner === data.p2);
    for (const nick of [data.p1, data.p2]) {
        const pRef = playerRef(room, nick);
        if (!(await get(pRef)).exists()) continue;   // ★ 강퇴된 노드 부활 금지
        const patch = { currentOpponent: null };
        if (winnerValid) patch[nick === data.winner ? 'wins' : 'losses'] = increment(1);
        await update(pRef, patch);
    }
}
```

세 가지가 전부 실전에서 나온 규칙이다:

- **`increment()`를 쓰는 이유**: `runTransaction`은 해당 경로의 로컬 캐시가 없으면 첫 콜백에 `null`을 넘긴다. 무심코 `return {wins:1}` 하면 기존 전적이 통째로 덮인다. 카운터는 서버 원자 연산 `increment()`가 정답.
- **`get()` 존재 확인**: 정산과 강퇴가 겹치면 삭제된 학생이 `{wins:1}`짜리 유령으로 부활한다.
- **호출은 여러 곳에서**: unsubMatch의 finished 감지, resolveMyMatch의 정리, 강퇴 핸들러, 재접속 정리 — 도장 덕에 전부 안전하다.

대안으로 **개인 도장**(`matches/{id}/counted/{me}`: 각자 자기 결과만 선점 후 자기 전적 증가)이 있다. 판이 짧고 결과가 자명하며 상대가 이미 떠났어도 내 기록은 남겨야 하는 게임(가위바위보)에 맞다. 제3자(강퇴·서버·정체감지)가 결과를 확정하는 게임은 공용 도장이 맞다. 템플릿은 공용 도장을 기본으로 한다.

### 7.3 종료 후 정리

복귀 시 포인터를 null로, 그리고 **양쪽 모두 떠난 경기는 `matches/{id}`를 삭제**해 방이 무한히 무거워지는 것을 막는다(상대 포인터가 여전히 이 경기를 가리키면 남겨둔다).

## 8. 이탈·정체·탈출 — 4중 방어

혼자 남아 무한 대기하는 학생이 생기지 않게 층을 나눈다.

| 층 | 감지 주체 | 잡는 것 | 지연 |
|---|---|---|---|
| **1. match onDisconnect** | 서버 | 브라우저 종료·단절 (**양쪽 동시 종료 포함**) | 즉시~수십 초 |
| **2. 상대 감시** | 상대 클라이언트 | 조용한 끊김(하트비트 노후화)·장기 away | AFK 한계 |
| **3. visibility 유예 → 자진 처리** | 본인 | 앱 전환·화면 잠금 후 미복귀 | GRACE 후 |
| **4. 정체 감지 + 탈출 버튼** | 상대/본인 | **상대가 살아 있는데 경기에 못 들어온 경우** | STALL 후 |

층 4가 v1 이후 추가된 부분이다. 층 1~3은 전부 "상대가 죽었는가"를 보는데, 실제 사고는 상대가 **멀쩡히 대기실 화면을 보고 있어서**(매칭 성사를 놓침) 하트비트가 계속 신선한 경우였다. 이때는:

- **정체 감지**: 한 수도 없이 (탈출버튼 시간 + STALL) 경과 → `endReason:'error'`, **승패 없이** 양쪽 대기실 복귀. 상대 잘못이 아니므로 몰수패를 주면 전적이 오염된다.
- **탈출 버튼**: 첫 행동 전 40초 뒤 노출, 클릭 시 `abandoned`(승패 없음). **한 수라도 두어지면 영구 숨김** — 지는 판 도망 방지.

상대 감시 구현의 3원칙: ① `opponentSynced` 가드(첫 스냅샷 전 판정 금지) ② 하트비트 **값의 변화 시각을 로컬로** 기록(서버 값끼리 빼면 시계 오차에 취약) ③ 판정 즉시 구독 해제(몰수 반복 호출 방지).

유예(GRACE)는 필수다 — 알림 확인·화면 자동 잠금 오탐이 교실에서 끊임없이 난다. 값은 판 길이의 30~50%.

## 9. 재접속 로직

핵심 원리: **입장 코드는 첫 입장과 재접속을 구분하지 않는다.** 나갈 때 서버에 남긴 흔적(onDisconnect 결과 + 포인터)을 같은 관문이 읽어 세 갈래로 보낸다.

### 9.1 관문 5단계

```
① 노드 판독      prev = get(players/{me}); 필수 필드가 온전한가(isComplete)?
                 → 손상 노드(구버전 사고 잔재)는 재접속이 아니라 '새로 생성'으로 복구
② 중복/유령 판정  looksOnline = status≠offline && (now−hb) < 40초
                 → 참이면 하드 차단이 아니라 customConfirm("이어서 접속할까요?")
③ 세션 인수      새 sessionId 기록 → 옛 기기가 스스로 물러남 (4장)
④ 경기 복구 확인  resolveMyMatch() — 항상 서버에서 포인터 직접 읽기
⑤ 분기           존재 && 오래 끊김(>40초 or 65초) → 경기 정리(무효/몰수) + 안내 → 대기실
                 존재 && 짧은 순단              → 하던 판으로 복귀 (선택 상태까지 복원)
                 없음                          → 대기실
```

### 9.2 왜 "차단"이 아니라 "확인 후 인수"인가 (자기 유령 문제)

와이파이가 팅긴 학생이 20초 만에 재접속하면, 서버가 아직 끊김을 감지하기 전이라 **자기 자신의 유령이 online으로 남아 있다.** 하드 차단은 본인을 최대 60초간 자기 이름에서 쫓아낸다("선생님, 제 이름이 사용 중이래요"). 확인창으로 열어두면: 본인이면 즉시 이어받고, 진짜 다른 기기라도 ③에서 스스로 물러나므로 안전하다. 확인창 문구에는 반드시 "**다른 친구가 쓰는 이름이라면 취소**" 경고를 넣는다 — 공용 태블릿 + 자동 입력 조합의 위험(13장) 때문이다.

### 9.3 침묵 패배 방지

경기 중 이탈은 대부분 층 1·2가 먼저 끝내버리므로, 재접속자는 이미 finished인 경기를 만난다. 이때 **아무 말 없이 대기실에 떨어뜨리면 패(또는 무효)가 몰래 올라가 있다.** ⑤에서 정리할 때 결과 안내 모달을 한 번 띄운다.

### 9.4 알고 있어야 할 남은 모서리 (미해결·의도적 보류)

- **유령 예약의 뒤늦은 발동**: 이어받아 판에 복귀해도, 옛 연결의 match onDisconnect는 취소할 수 없어(3.3) 수십 초 뒤 그 판이 몰수될 수 있다. 기존에는 입장 자체가 안 됐으니 순손실은 아니며, 근본 해결은 아래와 같은 구조 변경.
- **동시 끊김 승자 뒤집힘**: onDisconnect는 트랜잭션이 아니라 **일반 update**다. 양쪽이 동시에 끊기면 나중 예약이 먼저 것을 덮어 "먼저 끊긴 쪽이 이기는" 역전이 가능하다. 근본 해결은 예약이 승자를 직접 쓰지 않고 `disconnectedAt/{me}`만 남긴 뒤 산 자·재접속자가 트랜잭션으로 판정하는 구조인데, 변경 폭이 커서 실제 문제가 관찰되면 손대기로 보류.

## 10. 정책 스위치 — 게임마다 바뀌는 것

세 게임을 통일하고 남은 **의도된 차이**는 결국 상수 몇 개다. 축은 "한 판의 길이" 하나.

| 스위치 | 짧은 판 (수십 초) | 긴 판 (수 분) | 근거 |
|---|---|---|---|
| `AWAY_AS_LOSS` | **false — 무효** | **true — 몰수패** | 10초 판에서 알림 한 번에 패배가 찍히면 승률 수업 데이터가 오염. 5분 판에서 무효로 빼주면 상대가 5분을 날림 |
| `PARTNER_PICK_RANDOM` | **true — 무작위** | 취향 (선입선출 가능) | 상대빈도 수업은 표본 독립성 때문에 무작위가 **필수**. 선두는 어차피 반드시 매칭되므로 대기 공정성과 양립 |
| `AWAY_GRACE_MS` | 10~15초 | 60초+ | 판 길이의 30~50% |
| 무효 카운트 별도 필드 | `forfeits` 권장 | 불필요 | "승패에 포함되지 않습니다" 명시 — 데이터 위생 |
| 자동 복귀 | 3초 후 자동 | 버튼 클릭 | 판 회전 속도 |

턴 제한이 있는 게임은 타이머 기준을 반드시 서버가 기록한 `lastMoveTime`으로 — 새로고침으로 시간을 리셋하는 꼼수 차단. 카운트다운 표시는 매 틱 실제 시각으로 재계산(백그라운드 탭 스로틀링 대비).

## 11. 기본형(매칭 없는 게임) 패턴

블로토를 살리며 확립한, 매칭 없이도 지켜야 하는 것들.

**라운드 정산은 단일 원자 update로.** 모둠별로 나눠 쓰면 중간에 끊겼을 때 일부만 점수가 오른 채 남는다. 점수·잔여자원·라운드 전환·잠금 해제를 한 번의 다중 경로 update로 묶고, 적용 직전 **서버 상태를 새로 읽어 라운드 번호가 그대로인지** 확인한다(새로고침·중복 클릭의 이중 반영 방지).

**공개 연출 중 입력 잠금 + 스냅샷 채점.** 결과를 하나씩 공개하는 동안 학생이 값을 고치면 화면에 뜬 값과 점수가 어긋난다. 공개 시작 시 `state.revealing = 라운드`로 잠그고(학생 화면은 "결과 공개 중"), 채점은 공개 시작 시점에 떠 둔 **스냅샷 배열**로 한다 — 이중 방어. 잠금은 정산 update에 `revealing: null`을 포함해 해제하고, 실패 경로와 관리자 재진입 시에도 반드시 풀어준다(안 풀면 학생 영구 잠김).

**자동 진행은 취소 가능한 대기로.** `setTimeout` 핸들과 resolve 함수를 함께 보관해, 중지 버튼이 대기 중인 Promise를 즉시 깨우게 한다. 그냥 clearTimeout만 하면 await가 영원히 매달린다.

**연출 중 재렌더 차단.** `isAnimating` 플래그로 onValue 렌더를 막아 카드 DOM을 유지한다(하트비트 스냅샷이 연출을 지우는 사고 방지).

**학생은 자기 노드만 구독.** 다른 모둠의 제출값을 받으면 트래픽 낭비이자 **정보 노출**(블로토는 제출값이 비밀)이다.

## 12. 관리자 대시보드 규약

세 게임에서 수렴한 공통 규약. 새 게임도 이대로.

- **상태 판정은 `statusInfo()` 한 곳**: 접속중(녹, `#198754`) / 다른화면(노랑, `#ffc107`) / 접속 끊김(빨강, `#dc3545`). 판정은 `status` 값 + **하트비트 신선도(40초)** 둘 다 — status만 믿으면 조용히 끊긴 기기가 online으로 남는다.
- **테이블 서식 통일**: `table table-hover text-center align-middle mb-0` + `<thead class="table-light">`. 셀 강조는 부트스트랩 유틸(`fw-bold text-primary` 등)로.
- **정렬**: 기본은 입장순(`joinedAt` 오름차순, 재접속에도 불변). 대전 게임은 접속상태 1순위 → 승수 2순위도 좋다. 알파벳 정렬은 쓰지 않는다(정수형 닉네임의 키 순서 함정 포함).
- **matches를 구독하지 않는다**: 대전 현황은 `players/{id}/currentOpponent`로.
- **렌더 스로틀 1초 + 5초 주기 재렌더**: 하트비트마다 표를 다시 그리지 않고, 조용히 끊긴 학생의 표시는 주기 렌더(DB 읽기 없음)로 갱신.
- **방 코드**: 혼동 문자(0/O, 1/I) 제외 32자셋 + 존재 확인 재시도(≤20회).
- **방 삭제 순서**: 구독 해제 → remove → UI 초기화 → 목록 갱신. 구독을 먼저 끊어야 빈 스냅샷 깜빡임·오류가 없다. 삭제 중 버튼 잠금.
- **강퇴**: 진행 중 경기를 `finishMatchAtomic`+`settleMatch`로 정리한 뒤 waiting·player 노드 삭제. 도장 덕에 이중 정산 없음.
- **시간 흐름별 기록 표**(라운드별 등)는 최초 기록 시각(`createdAt`)으로 정렬하고, **수정 시에는 `updatedAt`만 갱신**해 위치가 유지되게 한다.

## 13. 첫화면 규약

`renderRoomEntrance` 하나로 통일. 페이지별 코드는 옵션 객체가 전부다.

- **입장 정보 기억**: 성공 시점에만 `rememberEntrance(code, nickname)` 호출(실패한 입력이 저장되지 않도록 자동 저장 금지). 방 코드는 **페이지 경로별**, 닉네임은 **전역** 키로 저장 — 같은 학생이 다른 게임에서도 이름이 채워진다. 불러올 때는 저장값도 입력과 같은 규칙으로 재정제(4자 대문자, 금지문자 제거).
- **공용 기기 대비**: 자동 입력 시 "지난 접속 정보를 불러왔어요 · **내 정보가 아니에요 (지우기)**" 링크 필수. 이어받기 허용(9.2)과 자동 입력이 결합하면 앞 학생의 세션을 뒷 학생이 실수로 인수할 수 있다 — 확인창의 빨간 경고 + 지우기 링크가 그 방어선이다.
- **게임방법 슬라이드**: `guideSlides` 배열만 넘기면 [방 입장하기]와 [대시보드 열기] 사이에 버튼이 생긴다. 안 넘기면 버튼 자체가 없다 — 페이지별 분기 코드 불필요. 자동 넘김 없이 학생이 직접 넘기게 한다.
- **입력 위생**: 닉네임은 DB 키로 쓰이므로 `. # $ [ ] /`·제어문자 즉시 제거 + 정규식 길이와 `maxlength` 동일값. 모든 출력은 `escapeHtml`.
- **오류는 원인별로**: onJoin 전체를 try/catch로 감싸고 permission 계열이면 "네트워크가 아니라 **보안 규칙** 문제"라고 구분해 안내. 안 그러면 모든 실패가 "네트워크 오류"로 뭉뚱그려져 진단이 안 된다(실제로 겪음).
- **모달 접근성**: 닫기 직전 `hide.bs.modal`에서 내부 포커스를 blur — aria-hidden 경고 방지. X·ESC·배경클릭까지 커버된다.

## 14. 보안 규칙 설계

클라이언트 전용 구조에서 규칙은 유일한 서버측 방어선이다. 대원칙과 실제로 밟은 함정.

### 14.1 대원칙

```json
{
  "rules": {
    ".read": false, ".write": false,          // 루트는 명시적으로 잠금
    "{GAME}_rooms": {
      ".read": true,                          // ★ 컬렉션 '자체'에 — 방 목록용
      "$room": {
        ".write": true,
        "...": "validate로 구조·값 검증"
      }
    }
  }
}
```

### 14.2 함정 목록 (전부 실제 사고)

1. **컬렉션 목록 읽기는 컬렉션 자체의 `.read`가 필요하다.** `$room` 하위에만 있으면 `get(ref(db,'rooms'))`가 거부되어 대시보드 드롭다운이 조용히 빈다. `.read`는 아래로만 흐른다.
2. **`hasChildren` 필드명은 코드의 실제 필드명과 대조하라.** 오목의 `joinedAt`을 가위바위보 규칙에 복사했다가(실제 필드는 `ts`) **모든 대기열 쓰기가 전멸**했다. 증상은 학생 입장 불가 + 10초마다 permission_denied 로그.
3. **null 가능 필드를 필수로 넣지 마라.** RTDB는 null을 저장하지 않는다(필드가 아예 생략됨). `last: null`인 첫 대기자는 `hasChildren([...,'last'])`에 매번 걸린다.
4. **`update()`는 병합 결과로 검증된다.** 그래서 부분 갱신(하트비트 등)이 `hasChildren`을 통과한다. 반대로 **트랜잭션은 노드 전체를 다시 쓰므로** 필수 필드가 없는 옛/손상 데이터에서 거부된다 — 규칙 강화 전 기존 방 정리 필수.
5. **삭제(null 쓰기)는 validate를 타지 않는다.** "지우고 새로 만들기" 우회는 규칙만으로 못 막는다.
6. **`matchLock`에는 TTL 상한** `until <= now + 15000` — 콘솔로 먼 미래 값을 박는 영구 잠금 차단. 규칙의 `now`는 서버 시각.
7. **전적 검증은 increment 호환으로**: `유지 또는 +1`만 허용(`newData.val() === data.val() || === data.val()+1`). 신규 생성은 열어두되(`!data.exists() || ...`), `=== 0` 강제는 정상 흐름을 막을 수 있어 피한다.
8. **상한 있는 증가**: 단조 증가만 걸면 999 점프가 통과한다. `<= data.val() + K` (K = 한 번에 오를 수 있는 최댓값). K를 정하는 설정(예: 모둠 수 상한)을 바꾸면 규칙도 함께.
9. **역행 금지**: `status`는 `finished → playing` 전이 차단, `statsApplied`는 `=== true`만 — 끝난 경기 되살려 재정산시키는 조작 차단.
10. **키-값 일치**: `nickname`은 `newData.val() === $nick` — 남의 이름으로 데이터 심기 차단 + 렌더 필터 정합성.
11. **`root.child()` 교차 참조**로 다른 노드 값 검증 가능(예: 출전 수 ≤ 잔여 병사). 단, 트랜잭션이 노드 전체를 재작성하는 게임에선 **"기존 값 그대로면 통과"** 예외를 함께 넣어야 하트비트가 안 막힌다.
12. **남는 한계를 알고 써라**: 인증이 없으면 방 삭제, +1 반복 파밍, 남의 노드 삭제는 못 막는다. 콘솔을 여는 학생이 실제로 관찰되면 그때 Firebase **Anonymous Auth**를 붙여 "자기 uid 노드만 수정 / 방 삭제는 교사 uid만"으로 올린다. `sessionId`가 그 수제 전신이라 이식이 자연스럽다.

## 15. 함정 대사전

14장의 규칙 함정 외 전부. 표의 모든 행이 이 프로젝트에서 실제로 발생했다.

### RTDB · SDK

| 함정 | 증상 | 해법 |
|---|---|---|
| 트랜잭션 첫 콜백의 `null` | 기존 전적이 통째로 덮임 | 카운터는 `increment()`, 또는 `get()` 존재 확인 후 `update()` |
| 트랜잭션 안 `serverTimestamp()` | 센티널이 그대로 저장되어 시간 계산 붕괴 | 트랜잭션 안에서는 `serverNow()` 값 |
| 트랜잭션 중단법 혼동 | 의도치 않은 쓰기 | 중단은 `return;`(undefined), 성공 판정은 `res.committed` |
| **`set()`에 merge 옵션 없음** (Firestore 혼동) | 세 번째 인자 무시, **노드 통째 덮임** → 닉네임·점수 소멸, 현황판 전멸 | 부분 갱신은 `update()`, 하위 경로 update |
| **Firestore API 혼입** (`updateDoc`, `doc`) | ReferenceError — 해당 기능 전체 무동작 | RTDB는 `update(ref(...))`만 |
| **빈 객체는 저장 안 됨** | `rounds: {}`가 사라져 `p.rounds[r]`에서 TypeError → 렌더 전멸 | 모든 접근에 `(p.rounds \|\| {})`, 생성 시 빈 객체 필드 생략 |
| **`numChildren()` vs `size`** | v9 모듈러엔 numChildren 없음 → TypeError. **첫 사람만 되고 둘째부터 실패**(exists 단락 때문) | `countChildren()` 안전판: size → numChildren → forEach 폴백 |
| 다중 경로 update 분할 | 반쪽 매칭·부분 정산 잔류 | 관련 변경은 단일 `update()` |
| onDisconnect는 일반 update | 동시 끊김 시 승자 뒤집힘 (9.4) | 인지하고 보류, 근본은 disconnectedAt 구조 |
| 다른 연결의 예약 취소 불가 | 인수 후 복귀한 판이 뒤늦게 몰수 (9.4) | 인지, 확인창 문구로 완화 |

### 매칭 · 상태

| 함정 | 증상 | 해법 |
|---|---|---|
| visible만으로 활성 판정 | 유령이 대기열 선두 점거 → **교실 전체 매칭 정지** | `alive` 신선도 25초 병행 (5장①) |

## 16. 새 게임 체크리스트

템플릿 기준의 실제 순서. (v1의 "13단계 처음부터 만들기"는 템플릿 등장으로 필요 없어졌다.)

### 17.1 상수 기본값 (세 게임 운영으로 수렴한 값)

| 상수 | 값 | 관계식 · 근거 |
|---|---|---|
| `HEARTBEAT_MS` | 10,000 | 기준값. 트래픽과 감지 지연의 균형 |

| `ONLINE_THRESHOLD_MS` | 40,000 | 하트비트 × 4 — 중복접속 판정·대시보드 끊김 표시 |

| `STALL_LIMIT_MS` | 60,000 | 정체 판정 추가 대기 |
| `ABANDON_BTN_MS` | 40,000 | 탈출 버튼 노출. 첫 수 이후 영구 숨김 |
| 폴링 주기 | 1,500 | 매칭 안전망. 로컬 캐시만 읽으므로 저비용 |
| 대시보드 렌더 | 스로틀 1s + 주기 5s | DB 읽기 없음 |
| 오목 전용 | TURN 30s / AFK 65s | AFK > 하트비트 × 6 |

**관계식이 값보다 중요하다**: `STALE = HB × 2.5`, `THRESHOLD = HB × 4`, `GRACE = 판 길이 × 0.3~0.5`, `AFK > HB × 6`. HEARTBEAT_MS를 바꾸면 전부 따라 움직인다.

### 17.2 endReason 사전

| 값 | 의미 | 승패 | 발생 주체 |
|---|---|---|---|
| (승리 판정) | 정상 종료 | 기록 | 행동 제출 트랜잭션 |
| `forfeit` | 이탈 유예 초과 | **정책**: 무효 또는 몰수패 | 본인(visibility) / 상대 감시 |
| `offline` | 연결 단절 | 정책 | 서버 onDisconnect / 상대 감시 / 재접속 정리 |
| `abandoned` | 수동 매칭 취소 | 없음 | 탈출 버튼 (첫 수 전만) |
| `error` | 정체(진입 실패)·상태 불일치 | **없음** — 상대 잘못 아님 | 정체 감지 |
| `kick` | 강퇴 | 정책 | 교사 |
| `pass` / `full` | 게임 규칙상 무승부 | 무승부 | 게임 로직 (오목: 연속 패스·판 가득) |

무효 계열(승패 없음)은 별도 카운트(`forfeits`)로 빼고 화면에 "승패에 포함되지 않습니다"를 명시한다 — 통계 수업의 데이터 위생.

### 마치며 — v2에서 다시 확인한 한 문장

이 아키텍처의 요지는 v1과 같다. **"모두가 동시에 실행해도 되는 코드 + 한 명만 통과하는 트랜잭션 관문 + 한 번에 끝내는 원자적 쓰기"**, 그리고 v2에서 추가된 반쪽: **"서버에 남긴 예약은 반드시 해제 규율과 함께, 규칙은 코드의 실제 필드와 대조하며."** 나머지는 전부 이 문장들의 각주다.

## 18. 스테이지형 학습게임 패턴 (기록형)

좀비헌터(정비례·반비례)를 다듬으며 확립한 세 번째 계열. 실시간 대전이 아니라 **개인 스테이지 진행 + 성취 기록**이 목적이므로 RTDB 대신 **Firestore**를 쓴다. 세션·하트비트·onDisconnect·매칭이 전부 없다 — 학생 기기는 저장 두 시점 외에는 DB를 건드리지 않는다.

### 18.1 스테이지 구조 규약

- **개념 스테이지 N개 + 마지막 혼합 스테이지 1개**(무한 모드). 스테이지당 **3문제**: 1·2번은 현재 개념의 새 문제, **3번은 이전 개념 복습**(무작위 1개). 1스테이지는 복습할 게 없으니 3번도 자기 개념, 요소 수만 복습 규칙을 따른다.
- **문제별 요소 수(난이도)**: 1번 4개 → 2번 3개 → 3번 2~3개 무작위. 새 개념은 연습량을 주고, 복습은 가볍게.
- **혼합 스테이지의 첫 문제를 깨는 순간이 상수준 판정 시점**이다. `saveClearRecord`(isCompleted=true)를 즉시 남기고 무한 챌린지를 계속한다. "플레이 종료" 버튼의 isClear 판정, 대시보드의 성취 '상' 판정도 전부 같은 기준으로 맞춘다 — 기준이 셋으로 갈라지면 대시보드와 학생 화면이 서로 다른 말을 한다.
- **혼합 스테이지 시도 제한 = 필요 최소 횟수 + 1** (예: 곡선 2개면 레이저 3발). 시도가 남아있는 동안은 **실패해도 목숨 유지**. **시도 소진 + 목표 잔존이면 목숨 1 차감 → 새 배치 생성 + 시도 리필**. 소진 상태(0회)로 화면에 머무는 경로를 아예 없애는 게 핵심이다 — 소진 후에도 계속 시도할 수 있게 두면 제한이 무의미해지고 "0발인데 목숨이 안 깎이는" 버그가 된다(실제로 겪음).

### 18.2 출제 정합성 (실제로 겪음)

- **표시 공간을 줄이면 출제 풀을 전수 재검증하라.** 모바일 확대를 위해 격자를 ±10→±8로 줄이자 y=5x의 격자점이 2개뿐이 되어 "1번 문제 요소 4개" 규칙이 조용히 깨졌다. 모든 출제 파라미터에 대해 *배치 가능한 자리 수 ≥ 문제당 요소 수*를 스크립트로 확인하고, 모자라는 파라미터는 풀에서 뺀다.
- **입력 범위 = 출제 범위.** 슬라이더가 ±24인데 출제 최대가 ±20이면 죽은 구간이 생기고, 반대면 못 맞히는 문제가 생긴다. 한쪽을 바꾸면 반드시 다른 쪽을 같이 바꾼다.

### 18.3 저장 규약 — 딱 두 시점

- Firestore 쓰기는 **gameOver(모든 판)와 saveClearRecord(상수준 달성)** 뿐이다. 진행 중 실시간 저장은 하지 않는다(무료 사용량 보호). 그 대가로 **중간 이탈(팅김) = 그 판 소실**임을 알고 설계한다.
- 보완은 **localStorage 스냅샷 이어하기**(DB 쓰기 0회): 문제 전환·UI 갱신 시 스냅샷 저장 → 재입장 시 같은 방·같은 이름·신선(수 시간 이내)이면 "이어서 하시겠습니까?" 확인 후 지점 복원. 목표 배치는 저장하지 않는다 — *같은 지점의 새 문제*면 충분하다. `beforeunload`에서의 DB 저장은 모바일에서 보장되지 않으므로 대안이 아니다.
- **스키마**: `{GAME_KEY}_records/{방}/records`(판별 원본: score, maxStage/maxProblem, isCompleted, totalAttempts/correctAttempts, conceptHits/conceptFails{1..N}, playTimeSec, playedAt) + `students/{닉네임}`(최신 요약, merge) + 방 문서(best* 필드). **대시보드 통계는 records만으로 재구성**한다 — 요약 필드가 깨져도 원본이 남는다.

### 18.4 대시보드 (12장 서식 규약 위에 얹는 것)

- **개념별 평균 정답률 막대**(conceptHits/Fails 합산), **성취 3단계**(상 = 상수준 기록 보유, 중 = 중반 개념 도달, 하), **평균 풀이 속도 분포**는 **20초 구간 + 마지막은 "60초 이상" 열린 구간**으로 — 구간을 닫아두면 최하위권이 표에서 사라진다.
- 학생 행 클릭 → **판별 이력 + 개념별 누적 모달**, 엑셀 내보내기(개념별 정답률 열은 CONCEPTS에서 동적 생성).

### 18.5 모바일 규약

- **767px 미만 컴팩트 미디어쿼리**: 상단 여백·헤더 패딩·컨트롤 간격·수식 크기·슬라이더 눈금을 일괄 축소(좀비헌터 기준 세로 약 180px 절약). **컨트롤은 균등 분할 행**(`.control-row > * { flex: 1 1 0; min-width: 0 }`)으로 — 선택 버튼들과 상태/수식 표시를 한 행에 넣으면 세로가 크게 준다.
- **캔버스는 범위를 줄이고 셀을 키워라**: ±10 격자·28px 셀 → ±8 격자·34px 셀 = 화면상 약 21% 확대. 축 숫자는 bold 20px 이상.
- **캔버스 내부에는 CSS 미디어쿼리가 통하지 않는다.** 다크모드 색 분기는 JS로: `matchMedia('(prefers-color-scheme: dark)')` 판정으로 축 숫자 색을 고르고, change 리스너에서 다시 그린다.
- **페이지 단독 라이트모드 강제는 실패했다**(실제로 겪음): `color-scheme: light only`는 공통 CSS의 `prefers-color-scheme` 미디어쿼리 판정을 바꾸지 못하고, `data-bs-theme` 속성 감시는 클래스 방식 테마를 놓친다. 테마 충돌은 **공통 CSS에서 원인을 찾아** 고치고, 페이지 쪽에서는 위처럼 다크 대응 색만 분기하라.

### 18.6 첫화면·엔진

- 첫화면은 **13장 그대로**: `renderRoomEntrance` + 성공 시점에만 `rememberEntrance`. 입장 검증은 방 존재 확인 + **다른 방 닉네임 중복 검사**(전 방 순회 — 명예의 전당이 방 통합이라 이름이 겹치면 기록이 섞인다).
